# Auction Service 상세 설계

## 1. 서비스 개요

| 항목 | 내용 |
|------|------|
| 서비스명 | auction-service |
| 포트 | 8084 |
| 아키텍처 | **Clean Architecture** (도메인별 4-Layer: presentation → application → domain ← infra) |
| DB | biddy_auction (PostgreSQL 16) |
| 캐시/Pub-Sub | Redis 7 |
| 통신 | REST (동기), Kafka (비동기), WebSocket (실시간) |
| Java | 21, Spring Boot 3.4, Spring Cloud 2024 |

경매 상태 관리, 입찰, 관심 경매, 실시간 입찰 구독 기능을 담당하는 도메인 서비스.
Auction, Bid, Watch 세 개의 독립 도메인으로 구성되며, 도메인 간 참조는 ID 기반으로 느슨하게 연관된다.

**설계 원칙: Auction은 경매 상태만 관리, 상품 정보는 Product Service 책임**
- Auction 테이블에 `productId`만 보관 (상품명, 브랜드, 이미지 등 미보관)
- 경매 피드/상세 화면은 **API Gateway/BFF에서 Product + Auction 응답을 조합**
- Product Service 장애 시 경매 상태(입찰/종료)는 독립 동작, 상품 정보만 미표시

### 2.1 경매 피드 조회

```

| 구분 | 항목 | 타입 | 필수 | 설명 |

| Query | page | int | N | 페이지 번호 (기본 0) |
| Query | size | int | N | 페이지 크기 (기본 20) |

**Response 200** (Auction Service 단독 응답 — 경매 상태 데이터만)
```json
{
  "content": [
    {
      "auctionId": "A-FNF97",
      "productId": "uuid-...",
      "sellerId": 10,
      "startPrice": 400000,
      "minIncrement": 20000,
      "currentBid": 720000,
      "bidCount": 6,
      "endsAt": "2026-06-12T15:30:00",
      "watcherCount": 88,
      "status": "LIVE"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 150,
  "totalPages": 8
}
```

> **상품 정보(name, brand, thumbnailUrl 등)는 Auction 응답에 포함하지 않음.**
> API Gateway/BFF에서 `productId` 목록으로 Product Service를 호출하여 조합.
>
> ```
> Gateway 조합 응답 (최종 클라이언트 수신):
>   Auction 데이터 + Product 데이터 merge
>   → name, brand, thumbnailUrl 등이 추가됨
> ```

**Response 200 (ENDED 상태 - 낙찰)**
```json
{
  "auctionId": "A-FNF97",
  "status": "ENDED",
  "currentBid": 740000,
  "result": {
    "type": "SOLD",
    "winnerId": 42,
    "winnerNickname": "collector01",
    "finalBid": 740000,
    "endedAt": "2026-06-12T15:30:00",
    "paymentDeadline": "2026-06-13T15:30:00",
    "paymentStatus": "PENDING"
  }
}
```

**Response 200 (ENDED 상태 - 유찰)**
```json
{
  "auctionId": "A-FNF97",
  "status": "ENDED",
  "currentBid": 0,
  "result": {
    "type": "UNSOLD",
    "winnerId": null,
    "finalBid": null,
    "endedAt": "2026-06-12T15:30:00"
  }
}
```

> `status`: `LIVE` | `ENDED`
> `isWatching`, `myHighestBid`: 인증된 사용자에게만 값 제공
> `result`: ENDED 상태에서만 값 제공, LIVE일 때는 null
> `result.type`: `SOLD` (낙찰) | `UNSOLD` (유찰)
> `result.paymentStatus`: `PENDING` | `PAID` | `TIMEOUT` (낙찰 시에만)

### 2.3 경매 등록 (Product Service → Kafka → Auction Service)

> Auction Service에 직접 POST API가 아닌, **Product Service에서 경매 상품 등록 시
> Kafka로 이벤트를 발행하여 Auction Service가 자동 생성**한다.

```
프론트 → POST /api/v1/products (Product Service)
         { type: "AUCTION", name, brand, edition, category,
           startPrice, minIncrement, endsAt, images }

Product Service:
  @Transactional
  1. product INSERT (type=AUCTION)
  2. Kafka 발행 (product.auction.registered)

  → Kafka payload: { productId, sellerId, startPrice, minIncrement, startsAt, endsAt }
  → Auction Service Consumer → auction INSERT (productId + 경매 설정만 저장)
```

**도메인 책임 분리**
- **Product Service 책임**: 상품명, 브랜드, 에디션, 카테고리, 설명, 이미지, 판매자 정보
- **Auction Service 책임**: productId 참조 + 경매 상태(가격, 입찰, 시간, 낙찰자)
- Auction 테이블에 상품 정보(name, brand 등)를 저장하지 않음
- 경매 피드/상세 화면은 **API Gateway/BFF에서 조합**

상세 설계: `06_도메인간_이벤트_흐름_정의.md` 참조

### 2.11 경매 종료 후 전체 API 흐름

```
경매 종료 시각 도달
    │
    ▼
[Internal] AuctionCloseScheduler
    │
    ├── 입찰 있음 ──────────────────────────────────────┐
    │   → status = ENDED                                │
    │   → Kafka: auction.ended (SOLD)                   │
    │   → WebSocket: ENDED push                         │
    │                                                   ▼
    │                                    ┌──────────────────────────┐
    │                                    │ 낙찰자: 결제 기한 24시간  │
    │                                    └──────────┬───────────────┘
    │                                               │
    │                                    ┌──────────┴──────────┐
    │                                    │                     │
    │                                결제 완료              기한 초과
    │                                    │                     │
    │                                    ▼                     ▼
    │                            주문/결제 완료         입찰자 제재
    │                            (Order/Payment)       + 유찰 재처리
    │                                                  (Kafka: payment.timeout)
    │
    └── 입찰 없음
        → status = ENDED
        → Kafka: auction.ended (UNSOLD)
        → 판매자 알림: "유찰되었습니다"
```

**경매 종료 후 사용되는 API/이벤트**

| 순서 | 주체 | API / 이벤트 | 설명 |
|------|------|-------------|------|
| 1 | Scheduler | (Internal) | `ends_at <= NOW()` 경매 종료 처리 |
| 2 | Auction → Kafka | `auction.ended` | 낙찰/유찰 이벤트 발행 |
| 3 | Auction → Client | WebSocket ENDED | 실시간 종료 알림 |
| 4 | Client → Auction | `GET /api/v1/auctions/{id}` | 종료된 경매 상세 (result 포함) |
| 5 | Client → Auction | `GET /api/v1/auctions/{id}/result` | 낙찰 결과 전용 조회 |
| 6 | Order → Auction | Kafka consume `auction.ended` | 낙찰 주문 자동 생성 |
| 7 | Payment → Order | 결제 처리 | 24시간 내 결제 |
| 8 | Payment → Kafka | `payment.completed` / `payment.timeout` | 결제 결과 이벤트 |
| 9 | Auction ← Kafka | consume `payment.timeout` | 유찰 재처리 + 제재 |

## 3. ERD

### 3.1 auction 테이블

> **Auction은 경매 상태만 관리. 상품 정보(name, brand 등)는 Product Service 책임.**

| 컬럼 | 타입 | 제약조건 | 설명 |
|------|------|----------|------|
| auction_id | VARCHAR(20) | PK | 경매 ID (e.g. A-FNF97) |
| product_id | UUID | NOT NULL, UNIQUE | Product Service 상품 ID (참조용) |
| seller_id | BIGINT | NOT NULL | 판매자 회원 ID |
| start_price | BIGINT | NOT NULL | 시작 가격 |
| min_increment | BIGINT | NOT NULL | 최소 입찰 단위 |
| current_bid | BIGINT | NOT NULL, DEFAULT 0 | 현재 최고 입찰가 |
| bid_count | INT | NOT NULL, DEFAULT 0 | 총 입찰 횟수 |
| watcher_count | INT | NOT NULL, DEFAULT 0 | 관심 등록 수 |
| status | VARCHAR(10) | NOT NULL, DEFAULT 'LIVE' | LIVE, ENDED |
| starts_at | TIMESTAMP | | 경매 시작 시각 |
| ends_at | TIMESTAMP | NOT NULL | 경매 종료 시각 |
| winner_id | BIGINT | | 낙찰자 회원 ID (종료 후 확정) |
| winning_bid_id | BIGINT | | 낙찰 입찰 ID (종료 후 확정) |
| created_at | TIMESTAMP | NOT NULL, DEFAULT now() | 등록 시각 |
| updated_at | TIMESTAMP | NOT NULL, DEFAULT now() | 수정 시각 |

**제거된 컬럼 (v1 대비)**

| 컬럼 | 이유 |
|------|------|
| `name`, `brand`, `edition` | Product Service 책임 → 비정규화 제거 |
| `category`, `description` | Product Service 책임 |
| `thumbnail_url` | Product Service 책임 |

**추가된 컬럼 (v1 대비)**

| 컬럼 | 이유 |
|------|------|
| `product_id` | Product 참조 (Gateway 조합 키) |
| `starts_at` | 예약 경매 지원 |
| `winner_id` | 낙찰 결과 즉시 조회 (bid 테이블 재조회 불필요) |
| `winning_bid_id` | 낙찰 입찰 추적 |

### 3.2 bid 테이블

| 컬럼 | 타입 | 제약조건 | 설명 |
|------|------|----------|------|
| bid_id | BIGSERIAL | PK | 입찰 ID |
| auction_id | VARCHAR(20) | NOT NULL, FK → auction | 경매 ID |
| bidder_id | BIGINT | NOT NULL, FK(외부) | 입찰자 회원 ID |
| amount | BIGINT | NOT NULL | 입찰 금액 |
| bid_at | TIMESTAMP | NOT NULL, DEFAULT now() | 입찰 시각 |

- INDEX: `(auction_id, bid_at DESC)` — 입찰 내역 최신순 조회용
- INDEX: `(auction_id, amount DESC)` — 최고 입찰 조회용

### 3.3 auction_watch 테이블

| 컬럼 | 타입 | 제약조건 | 설명 |
|------|------|----------|------|
| watch_id | BIGSERIAL | PK | 관심 ID |
| auction_id | VARCHAR(20) | NOT NULL, FK → auction | 경매 ID |
| member_id | BIGINT | NOT NULL, FK(외부) | 회원 ID |
| created_at | TIMESTAMP | NOT NULL, DEFAULT now() | 등록 시각 |

- UNIQUE: `(auction_id, member_id)` — 중복 관심 등록 방지

### 3.4 설계 변경 노트

> v1에서는 `auction_image` 테이블이 있었으나, 이미지는 Product Service 책임이므로 제거.
> v1에서 비정규화 저장하던 상품 정보(name, brand 등)도 제거. `productId`만 보관.

> `auction_image` 테이블 제거 — 이미지는 Product Service 책임

## 4. Kafka 이벤트

### 4.1 Produce (발행)

| 토픽 | 이벤트 | 트리거 | 설명 |
|------|--------|--------|------|
| `auction.ended` | AuctionEndedEvent | 경매 종료 시 (스케줄러) | 낙찰 결과를 Order에 전달 (주문 자동 생성) |

> **2026-07-15 업데이트**: `auction.ended` 이벤트는 **Transactional Outbox 패턴**을 적용하여 발행한다.
> 경매 종료 트랜잭션과 이벤트 발행의 원자성을 보장하여 이벤트 손실을 방지한다. (섹션 8 참조)

> 입찰 알림(`auction.bid`)은 Kafka가 아닌 **WebSocket 직접 push**로 처리.
> Auction 응답에 상품 정보가 없으므로, Order가 주문 생성 시 Product Service에서 상품 정보를 별도 조회.

**AuctionEndedEvent** (낙찰 → Order Service)
```json
{
  "eventType": "AUCTION_ENDED",
  "timestamp": "2026-06-12T15:30:00",
  "auctionId": "A-FNF97",
  "productId": "uuid-...",
  "sellerId": 10,
  "finalBid": 740000,
  "winnerId": 42,
  "paymentDeadline": "2026-06-13T15:30:00"
}
```

> 상품명, 브랜드, 썸네일 등은 포함하지 않음.
> Order Service가 `productId`로 Product Service에서 조회하여 주문 내역에 표시.

### 4.2 Consume (구독)

| 토픽 | 이벤트 | 처리 |
|------|--------|------|
| `product.auction.registered` | ProductAuctionRegisteredEvent | 경매 자동 생성 (productId + 경매 설정만 저장) |

> 결제 관련(`payment.completed`, `payment.timeout`)은 **Order/Payment 서비스 간 흐름**.
> Auction Service 범위 아님.

**ProductAuctionRegisteredEvent** (수신)
```json
{
  "productId": "uuid-...",
  "sellerId": 10,
  "startPrice": 400000,
  "minIncrement": 20000,
  "startsAt": "2026-06-20T10:00:00",
  "endsAt": "2026-06-20T15:00:00"
}
```

> 상품 정보(name, brand 등)는 포함하지 않음. Auction은 `productId`만 저장.

### 4.3 Auction Kafka 현황 (확정)

| 방향 | Topic | 역할 | Payload 핵심 필드 |
|------|-------|------|------------------|
| Product → **Auction** | `product.auction.registered` | 경매 자동 생성 | productId, sellerId, startPrice, minIncrement, endsAt |
| Auction → **Order** | `auction.ended` | 낙찰 주문 생성 | auctionId, productId, sellerId, finalBid, winnerId |

> 입찰 알림은 WebSocket 직접 push (Kafka 불필요).
> 결제 관련 이벤트는 Order/Payment 간 흐름 (Auction 범위 아님).

#### 이벤트 전체 흐름도

```
┌──────────────────────────────────────────────────────────┐
│                    Kafka Event Bus                         │
│                                                            │
│  product.auction.registered ──────┐                       │
│                                    ▼                       │
│                                 Auction                    │
│                              (경매 자동 생성)               │
│                                                            │
│  auction.ended ───────────────────┐                       │
│                                    ▼                       │
│                                 Order                      │
│                              (주문 자동 생성)               │
│                                                            │
│  입찰 알림 ──── WebSocket 직접 push → 프론트 (실시간)      │
│  종료 알림 ──── WebSocket 직접 push → 프론트 (실시간)      │
└──────────────────────────────────────────────────────────┘
```

#### 이벤트 설계 원칙

| 원칙 | 이유 |
|------|------|
| **ID 필드만 포함 (도메인 순수성)** | 상품 정보는 Product 책임, 필요 시 소비자가 Product API 호출 |
| **timestamp 필수** | 이벤트 순서 보장, 디버깅 |
| **eventType 필수** | 하나의 topic에서 여러 이벤트 타입 분기 가능 |
| **민감 정보 절대 제외** | 비밀번호, 카드번호, 주소 등 포함 금지 |

## 5. 핵심 비즈니스 규칙

### 5.1 입찰 검증

```
입찰 금액 >= currentBid + minIncrement
```

| 검증 항목 | 실패 시 응답 |
|-----------|-------------|
| 경매가 LIVE 상태인지 | 409 Conflict — 종료된 경매 |
| 입찰 금액 >= currentBid + minIncrement | 400 Bad Request — 최소 입찰 단위 미달 |
| 현재 최고 입찰보다 높은지 (동시성) | 409 Conflict — 이미 더 높은 입찰 존재 |
| 본인 경매에 입찰 불가 | 403 Forbidden |

### 5.2 동시성 제어

입찰은 동시 요청이 빈번하므로 **비관적 잠금(Pessimistic Lock)** 또는 **낙관적 잠금(Optimistic Lock + 재시도)** 적용.

```java
// 비관적 잠금 예시
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Auction a WHERE a.auctionId = :id")
Optional<Auction> findByIdForUpdate(@Param("id") String id);
```

### 5.3 경매 종료 처리

- **스케줄러**: `@Scheduled`로 주기적 만료 경매 확인 또는 각 경매별 `endsAt`에 맞춘 지연 작업
- 종료 시: `status`를 `ENDED`로 변경 → `auction.ended` 이벤트 발행
- 후속 처리: Order Service에서 낙찰 주문 자동 생성

## 6. 입찰 플로우 상세 설계

플로우차트 기반으로 입찰 진입 → 입찰 처리 → 경매 종료까지의 전체 흐름을 정의한다.

### 6.1 입찰 진입 플로우

사용자가 경매 상세 페이지에 진입한 시점부터 입찰 금액을 입력하기까지의 사전 검증 단계.

```
경매 상세 진입
    │
    ▼
경매 상세 페이지 렌더링
    │
    ▼
┌─────────────┐
│ 경매 상태?  │
└─────┬───────┘
      │
  ┌───┴───┐
  │종료   │진행중
  ▼       ▼
낙찰     로그인 여부 확인
프로세스      │
         ┌───┴───┐
         │아니요  │예
         ▼       ▼
     로그인    판매자 본인 여부
     화면유도      │
              ┌───┴───┐
              │예     │아니요
              ▼       ▼
          본인입찰  입찰 금액 입력
          불가안내
```

| 단계 | 검증 항목 | 실패 시 처리 | HTTP 상태 |
|------|-----------|-------------|-----------|
| 1 | 경매 상태 = LIVE | 종료된 경매 → 낙찰 프로세스로 라우팅 | 409 Conflict |
| 2 | 사용자 인증 여부 | 비로그인 → 로그인 화면 유도 (FE 처리) | 401 Unauthorized |
| 3 | 판매자 본인 여부 | sellerId == currentUserId → 입찰 거부 | 403 Forbidden |

### 6.2 입찰 처리 플로우

입찰 금액 제출 후 서버 내부의 검증-락-저장-알림 파이프라인.

```
입찰 금액 입력
    │
    ▼
┌───────────────┐
│ 1차 유효 검증 │ ← Application Layer (락 없이 빠른 검증)
└───────┬───────┘
        │ 통과
        ▼
  비관적 락 획득 ← SELECT ... FOR UPDATE
        │
        ▼
┌───────────────┐
│ 최종 유효 검증 │ ← 락 보유 상태에서 재검증
└───────┬───────┘
        │ 검증 통과
        ▼
  입찰 완료 (현재가 업데이트)
        │
        ├──────────────────┐
        ▼                  ▼
  이전 입찰자 알림    경쟁 패배 안내
  (WebSocket/Push)   (경쟁가 갱신 알림)
        │                  │
        └──────┬───────────┘
               ▼
       입찰 금액 입력 (재입찰 가능)
```

#### 6.2.1 1차 유효 검증 (Pre-Lock Validation)

락 획득 전 빠르게 수행하는 사전 검증. DB 락 대기 시간을 줄이기 위한 목적.

| 검증 항목 | 조건 | 실패 응답 |
|-----------|------|-----------|
| 경매 상태 | status == LIVE | 409 — 종료된 경매 |
| 최소 입찰 단위 | amount >= currentBid + minIncrement | 400 — 최소 입찰 단위 미달 |
| 본인 경매 여부 | bidderId != sellerId | 403 — 본인 입찰 불가 |

#### 6.2.2 비관적 락 획득 (Pessimistic Lock)

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Auction a WHERE a.auctionId = :id")
Optional<Auction> findByIdForUpdate(@Param("id") String id);
```

- 동시 입찰 요청에 대한 직렬화 보장
- 락 대기 타임아웃 설정 필요 (e.g. `javax.persistence.lock.timeout=3000`)
- 락 획득 실패 시 → 503 Service Unavailable 또는 재시도 안내

#### 6.2.3 최종 유효 검증 (Post-Lock Validation)

락을 잡은 상태에서 **최신 DB 값** 기반으로 재검증. 1차 검증과 락 획득 사이에 다른 트랜잭션이 값을 변경했을 수 있으므로 반드시 필요.

| 검증 항목 | 조건 | 실패 응답 |
|-----------|------|-----------|
| 경매 상태 (재확인) | status == LIVE | 409 — 종료된 경매 |
| 입찰 금액 (재확인) | amount >= currentBid + minIncrement | 409 — 이미 더 높은 입찰 존재 |

#### 6.2.4 입찰 완료 처리

하나의 트랜잭션 내에서 원자적으로 수행:

1. `bid` 레코드 INSERT — `bidRepository.save()`
2. `auction.current_bid` UPDATE — `auction.applyBid(amount)`
3. `auction.bid_count` INCREMENT — `auction.applyBid()` 내부
4. WebSocket 실시간 브로드캐스트 — `AuctionWebSocketPublisher.publishBid()`
5. (TODO) Kafka `auction.bid` 토픽 발행 — `BidPlacedEvent`

> 현재 구현: 1~4 완료. Kafka 발행은 다음 작업에서 추가 예정.

#### 6.2.5 이전 입찰자 알림

입찰 성공 시, **직전 최고 입찰자**에게 경쟁 패배 알림 전송.

| 알림 대상 | 채널 | 내용 | 구현 |
|-----------|------|------|------|
| 경매 구독자 전체 (이전 입찰자 포함) | WebSocket (`/topic/auctions/{auctionId}`) | BID 메시지 (currentBid, bidCount, bidderId) | `AuctionWebSocketPublisher.publishBid()` |

> Member Service 경유 없이 WebSocket으로 직접 push. 경매 페이지를 구독 중인 모든 사용자에게 전달.

### 6.3 경매 종료 플로우

경매 종료 시각 도달 시 스케줄러에 의해 자동 실행되는 낙찰/유찰 처리 흐름.

```
종료 시각 도달
    │
    ▼
종료 정보 수집
    │
    ▼
┌─────────────────┐
│ 입찰 내역 존재? │
└────┬────────────┘
     │
 ┌───┴───┐
 │없음   │있음
 ▼       ▼
유찰    최고 입찰자 낙찰
(미판매)     │
             ▼
       낙찰 알람 발송
             │
             ▼
     ┌──────────────────┐
     │ 24시간 이내 결제? │
     └────┬─────────────┘
          │
      ┌───┴────┐
      │아니요   │예
      ▼        ▼
  입찰자 제재  주문/결제 완료
  + 유찰처리   흐름
```

#### 6.3.1 종료 정보 수집

스케줄러가 `ends_at <= NOW()` AND `status = 'LIVE'`인 경매를 조회하여 종료 처리 대상 수집.

```java
@Scheduled(fixedDelay = 1000)
public void processExpiredAuctions() {
    List<Auction> expired = auctionRepository
        .findAllByStatusAndEndsAtBefore(AuctionStatus.LIVE, LocalDateTime.now());
    expired.forEach(this::closeAuction);
}
```

#### 6.3.2 유찰 처리 (입찰 내역 없음)

| 처리 항목 | 내용 |
|-----------|------|
| 상태 변경 | status → `ENDED` |
| 결과 기록 | 낙찰자 없음 (winnerId = null) |
| 이벤트 발행 | `AuctionEndedEvent` (winnerId = null) |
| WebSocket | UNSOLD 이벤트 브로드캐스트 (`AuctionWebSocketPublisher.publishUnsold()`) — 판매자가 경매 페이지 구독 중이면 직접 알림 |

#### 6.3.3 낙찰 처리 (입찰 내역 존재)

| 처리 항목 | 내용 |
|-----------|------|
| 상태 변경 | status → `ENDED` |
| 낙찰자 확정 | 최고 입찰 금액의 bidder를 winner로 확정 |
| 이벤트 발행 | `AuctionEndedEvent` (winnerId, finalBid 포함) |
| WebSocket | ENDED 이벤트 브로드캐스트 (`AuctionWebSocketPublisher.publishEnded()`) — 낙찰자/판매자가 경매 페이지 구독 중이면 직접 알림 |

#### 6.3.4 결제 기한 정책

| 항목 | 정책 |
|------|------|
| 결제 기한 | 낙찰 후 24시간 |
| 기한 내 결제 | Order Service → Payment Service 결제 완료 흐름 |
| 기한 초과 | 입찰자 제재 + 유찰 재처리 |

#### 6.3.5 결제 기한 초과 시 처리

| 처리 항목 | 내용 |
|-----------|------|
| 입찰자 제재 | 패널티 부과 (제재 이력 기록, 반복 시 이용 제한) |
| 유찰 재처리 | 해당 경매를 미판매 상태로 전환 |
| 판매자 알림 | "낙찰자가 결제를 완료하지 않아 유찰 처리되었습니다." |
| 이벤트 흐름 | Payment → Kafka → **Order** (주문 취소) → Kafka → **Auction** (유찰 재처리). Payment가 Auction을 직접 호출하지 않음 |

## 7. 패키지 구조 (Clean Architecture)

도메인별로 독립된 패키지를 가지며, 의존성 방향은 항상 **바깥 → 안쪽**으로 흐른다.

```
com.biddy.auction
├── AuctionApplication.java
│
├── common/                                    ── 공통 모듈 ──
│   ├── config/
│   │   └── JpaConfig.java                     @EnableJpaAuditing 전역 설정
│   ├── domain/
│   │   └── BaseEntity.java                    createdAt, updatedAt 자동 관리
│   └── exception/

### 7.1 레이어별 의존성 규칙

```
┌─────────────────────────────────────────────────────┐
│ presentation  →  application  →  domain  ←  infra   │
│ (Controller)     (Service)      (Entity)   (JPA)    │
│                  (UseCase)      (Port)     (Adapter) │
└─────────────────────────────────────────────────────┘
         ↓              ↓            ↑          ↑
    외부 요청 수신   비즈니스 로직   핵심 도메인   기술 구현
```

| 규칙 | 설명 |
|------|------|
| **Domain은 외부에 의존하지 않는다** | Entity, Repository Port는 순수 Java |
| **Application은 Domain만 의존** | UseCase/Service는 Repository Port만 참조 |
| **Infra는 Domain을 구현** | Adapter가 Repository Port를 implements |
| **Presentation은 Application만 의존** | Controller → UseCase 인터페이스 참조 |
| **도메인 간 참조는 ID 기반** | Bid → Auction 직접 참조 X, auctionId로 느슨한 연관 |

## 8. Transactional Outbox 패턴

**도입일**: 2026-07-15
**적용 범위**: `auction.ended` 이벤트 발행

### 8.1 개요

경매 종료 시 발행되는 `auction.ended` 이벤트에 **Transactional Outbox 패턴**을 적용하여 이벤트 발행의 원자성을 보장한다.

#### 문제점 (기존 방식)

```java
@Transactional
public void closeAuction(String auctionId) {
    auction.close();                          // DB 트랜잭션
    auctionRepository.save(auction);          // DB 트랜잭션
    kafkaTemplate.send("auction.ended", ...); // Kafka 발행 (별도)
}
```

| 시나리오 | 문제 |
|---------|-----|
| DB 커밋 성공 + Kafka 실패 | 경매는 종료되었으나 Order Service에 알림 없음 → 주문 미생성 |
| DB 롤백 + Kafka 성공 | 경매는 진행 중인데 Order Service가 주문 생성 → 데이터 불일치 |
| Kafka 지연/타임아웃 | 응답 시간 증가, 사용자 대기 |

#### 해결 방안 (Outbox 패턴)

비즈니스 트랜잭션과 **동일한 트랜잭션**에서 이벤트를 DB에 저장하고, 별도의 스케줄러가 주기적으로 Kafka로 발행한다.

```java
@Transactional
public void closeAuction(String auctionId) {
    auction.close();                     // DB 트랜잭션
    auctionRepository.save(auction);     // DB 트랜잭션

    // Outbox 테이블에 이벤트 저장 (동일 트랜잭션)
    OutboxEvent outboxEvent = OutboxEvent.builder()
        .aggregateType("AUCTION")
        .aggregateId(auctionId)
        .topic("auction.ended")
        .payload(json)
        .build();
    outboxEventRepository.save(outboxEvent);  // DB 트랜잭션

    // 커밋 → 경매 종료 + 이벤트 저장이 원자적으로 완료
}
```

별도 스케줄러가 5초마다 PENDING 이벤트를 Kafka로 발행:

```java
@Scheduled(fixedDelay = 5000)
@Transactional
public void relayOutboxEvents() {
    List<OutboxEvent> pending = outboxEventRepository
        .findTop100ByStatusOrderByCreatedAtAsc(PENDING);

    for (OutboxEvent event : pending) {
        kafkaTemplate.send(event.getTopic(), event.getPayload());
        event.markAsProcessed();
        outboxEventRepository.save(event);
    }
}
```

### 8.3 구현 컴포넌트

#### 8.3.1 Domain Layer

**OutboxEvent.java** (`auction/outbox/domain/OutboxEvent.java`)

```java
@Entity
@Table(name = "outbox_events")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class OutboxEvent {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 50)
    private String aggregateType;  // "AUCTION"

    @Column(nullable = false, length = 255)
    private String aggregateId;    // "A-TEST01"

    @Column(nullable = false, length = 100)
    private String topic;          // "auction.ended"

    @Column(nullable = false, columnDefinition = "TEXT")
    private String payload;        // JSON 직렬화된 AuctionEndedEvent

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private OutboxStatus status;   // PENDING, PROCESSED, FAILED

    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    private LocalDateTime processedAt;
    private LocalDateTime lastAttemptAt;

    @Column(nullable = false)
    private int retryCount;

    @Column(columnDefinition = "TEXT")
    private String lastError;

    @Builder
    public OutboxEvent(String aggregateType, String aggregateId,
                       String topic, String payload) {
        this.aggregateType = aggregateType;
        this.aggregateId = aggregateId;
        this.topic = topic;
        this.payload = payload;
        this.status = OutboxStatus.PENDING;
        this.retryCount = 0;
    }

    public void markAsProcessed() {
        this.status = OutboxStatus.PROCESSED;
        this.processedAt = LocalDateTime.now();
        this.lastAttemptAt = this.processedAt;
        this.lastError = null;
    }

    public void markAsFailed(Throwable throwable, int maxRetryCount) {
        this.retryCount++;
        this.lastAttemptAt = LocalDateTime.now();
        this.lastError = resolveErrorMessage(throwable);
        if (this.retryCount >= maxRetryCount) {
            this.status = OutboxStatus.FAILED;
        }
    }

    @PrePersist
    void prePersist() {
        this.createdAt = LocalDateTime.now();
    }

    private String resolveErrorMessage(Throwable throwable) {
        if (throwable == null) return null;
        String message = throwable.getMessage();
        if (message == null || message.isBlank()) {
            message = throwable.getClass().getSimpleName();
        }
        return message.length() > 1000 ? message.substring(0, 1000) : message;
    }
}
```

#### 8.3.2 Scheduler Layer

**OutboxRelayScheduler.java** (`auction/outbox/scheduler/OutboxRelayScheduler.java`)

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class OutboxRelayScheduler {

    private final OutboxEventRepository outboxEventRepository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Value("${outbox.scheduler.max-retry-count:5}")
    private int maxRetryCount;

    @Value("${outbox.scheduler.send-timeout-seconds:10}")
    private long sendTimeoutSeconds;

    @Scheduled(fixedDelayString = "${outbox.scheduler.delay:5000}")
    @Transactional
    public void relayOutboxEvents() {
        List<OutboxEvent> pendingEvents = outboxEventRepository
            .findTop100ByStatusOrderByCreatedAtAsc(OutboxStatus.PENDING);

        if (pendingEvents.isEmpty()) {
            return;
        }

        log.info("Relaying {} pending outbox events to Kafka...", pendingEvents.size());

        for (OutboxEvent event : pendingEvents) {
            try {
                kafkaTemplate.send(event.getTopic(), event.getAggregateId(), event.getPayload())
                        .get(sendTimeoutSeconds, TimeUnit.SECONDS);
                event.markAsProcessed();
                outboxEventRepository.save(event);
                log.info("Successfully relayed outbox event id: {} to topic {}",
                         event.getId(), event.getTopic());
            } catch (Exception e) {
                log.error("Unexpected error relaying outbox event id: {}", event.getId(), e);
                event.markAsFailed(e, maxRetryCount);
                outboxEventRepository.save(event);
            }
        }
    }
}
```

**스케줄러 동작 방식**:

1. 5초마다 실행 (기본값, 설정 가능)
2. PENDING 상태의 이벤트를 최대 100개 조회 (오래된 순)
3. Pessimistic Lock으로 조회 → 중복 발행 방지
4. 각 이벤트를 Kafka로 발행 (타임아웃 10초)
5. 성공 시: `PROCESSED`로 변경
6. 실패 시: `retryCount` 증가, 5회 초과 시 `FAILED`로 변경

@Slf4j
@Component
@RequiredArgsConstructor
public class AuctionEndedEventProducer {

    private static final String TOPIC = "auction.ended";

    private final OutboxEventRepository outboxEventRepository;
    private final ObjectMapper objectMapper;

    public void publish(Auction auction, Bid topBid) {
        AuctionEndedEventPayload payload = AuctionEndedEventPayload.from(auction, topBid);

        try {
            String json = objectMapper.writeValueAsString(payload);
            OutboxEvent outboxEvent = OutboxEvent.builder()
                    .aggregateType("AUCTION")
                    .aggregateId(auction.getAuctionId())
                    .topic(TOPIC)
                    .payload(json)
                    .build();
            outboxEventRepository.save(outboxEvent);

            log.info("Outbox 이벤트 저장: auctionId={}, winnerId={}, finalBid={}",
                    auction.getAuctionId(), topBid.getBidderId(), topBid.getAmount());
        } catch (JsonProcessingException e) {
            log.error("이벤트 직렬화 실패: auctionId={}", auction.getAuctionId(), e);
            throw new IllegalStateException("경매 종료 이벤트 직렬화에 실패했습니다.", e);
        }
    }
}
```

- 직렬화 실패 시 예외 발생 → 트랜잭션 롤백

### 8.6 장점

| 장점 | 설명 |
|------|------|
| **원자성 보장** | 경매 종료 + 이벤트 발행이 All-or-Nothing |
| **신뢰성** | Kafka 장애 시에도 이벤트 손실 없음 (DB에 저장) |
| **재시도** | 자동 재시도로 일시적 네트워크 장애 대응 |
| **추적성** | outbox_events 테이블에서 모든 이벤트 이력 확인 가능 |
| **동시성 제어** | Pessimistic Lock으로 중복 발행 방지 |
| **응답 시간 개선** | Kafka 발행을 비동기로 처리 → API 응답 시간 단축 |
| **독립성** | 비즈니스 로직과 메시지 발행 로직 분리 |

### 8.7 모니터링 및 운영

#### 모니터링 쿼리

**PENDING 이벤트 수 (지연 감지)**

```sql
SELECT COUNT(*) as pending_count,
       MIN(created_at) as oldest_event
FROM outbox_events
WHERE status = 'PENDING';
```

**FAILED 이벤트 조회 (장애 추적)**

```sql
SELECT id, aggregate_id, topic, retry_count, last_error, created_at
FROM outbox_events
WHERE status = 'FAILED'
ORDER BY created_at DESC
LIMIT 100;
```

**시간대별 이벤트 발행 현황**

```sql
SELECT
    DATE_TRUNC('hour', created_at) as hour,
    status,
    COUNT(*) as event_count
FROM outbox_events
WHERE created_at > NOW() - INTERVAL '24 hours'
GROUP BY hour, status
ORDER BY hour DESC, status;
```

#### 알람 기준

| 지표 | 임계값 | 조치 |
|------|--------|------|
| PENDING 이벤트 적체 | > 1000개 | Kafka 연결 상태 확인, 스케줄러 인스턴스 증설 |
| FAILED 이벤트 증가 | 시간당 > 10개 | Kafka 브로커 상태 확인, 에러 로그 분석 |
| 가장 오래된 PENDING | 생성 후 > 5분 | 스케줄러 동작 여부 확인 |

#### 재처리 방법

FAILED 이벤트를 수동으로 재처리:

```sql
-- FAILED → PENDING 변경 (스케줄러가 자동 재시도)
UPDATE outbox_events
SET status = 'PENDING',
    retry_count = 0,
    last_error = NULL
WHERE id IN (123, 456, 789);
```

#### 정리 정책

처리 완료된 이벤트 정리 (주기적 실행 권장):

```sql
-- 7일 이상 지난 PROCESSED 이벤트 삭제
DELETE FROM outbox_events
WHERE status = 'PROCESSED'
  AND processed_at < NOW() - INTERVAL '7 days';

-- 30일 이상 지난 FAILED 이벤트 아카이빙 후 삭제
INSERT INTO outbox_events_archive
SELECT * FROM outbox_events
WHERE status = 'FAILED'
  AND created_at < NOW() - INTERVAL '30 days';

DELETE FROM outbox_events
WHERE status = 'FAILED'
  AND created_at < NOW() - INTERVAL '30 days';
```

### 8.8 제약사항 및 주의사항

| 항목 | 내용 |
|------|------|
| **이벤트 순서 보장** | 동일 `aggregateId`에 대한 순서 보장 안 됨 (병렬 처리 시). 순서가 중요하면 Kafka 파티션 키 설정 필요 |
| **중복 발행 가능성** | At-Least-Once 보장. Consumer는 멱등성 처리 필수 |
| **스케줄러 다중 인스턴스** | Pessimistic Lock으로 중복 방지하나, DB 부하 증가 가능 |
| **대용량 처리** | 이벤트 적체 시 배치 크기(100개) 조정 또는 스케줄러 주기 단축 고려 |
| **트랜잭션 타임아웃** | Outbox 저장으로 트랜잭션 시간 증가 → 타임아웃 설정 검토 |

### 8.9 향후 개선 방안

| 개선 방안 | 효과 |
|-----------|------|
| **CDC (Change Data Capture)** | Debezium 등으로 DB 변경 스트림 직접 구독 → 스케줄러 제거 |
| **Dead Letter Queue** | FAILED 이벤트를 별도 Kafka 토픽으로 이동 → 수동 재처리 간소화 |
| **파티션 키 설정** | Kafka 발행 시 `aggregateId`를 파티션 키로 사용 → 순서 보장 |

## 9. WebSocket 실시간 통신

**프로토콜**: STOMP over WebSocket
**구현**: Spring WebSocket + SockJS fallback

### 9.1 개요

경매 서비스는 입찰 발생 및 경매 종료 이벤트를 실시간으로 클라이언트에 전달하기 위해 WebSocket을 사용한다. STOMP 프로토콜을 통해 Pub/Sub 패턴으로 구현되며, WebSocket을 지원하지 않는 환경에서는 SockJS fallback을 제공한다.

#### 주요 특징

| 특징 | 설명 |
|------|------|
| **프로토콜** | STOMP (Simple Text Oriented Messaging Protocol) |
| **연결 방식** | WebSocket (ws:// 또는 wss://) + SockJS fallback |
| **메시지 패턴** | Pub/Sub (1:N 브로드캐스트) |
| **토픽 구조** | `/topic/auctions/{auctionId}` - 경매별 독립 채널 |
| **메시지 타입** | BID (입찰 발생), ENDED (경매 종료) |
| **인증** | 현재 미적용 (향후 JWT 기반 인증 추가 예정) |

### 9.2 WebSocket 엔드포인트 설정

**WebSocketConfig.java** (`auction/common/config/WebSocketConfig.java`)

```java
@Configuration
@EnableWebSocketMessageBroker
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void configureMessageBroker(MessageBrokerRegistry config) {
        config.enableSimpleBroker("/topic");  // 브로드캐스트 채널 prefix
        config.setApplicationDestinationPrefixes("/app");  // 클라이언트→서버 메시지 prefix
    }

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        // 순수 WebSocket (STOMP.js 클라이언트용)
        registry.addEndpoint("/ws")
                .setAllowedOriginPatterns("*");

        // SockJS fallback (WebSocket 미지원 환경용)
        registry.addEndpoint("/ws-sockjs")
                .setAllowedOriginPatterns("*")
                .withSockJS();
    }
}
```

**엔드포인트**:
- `/ws` - 순수 WebSocket 연결 (권장)
- `/ws-sockjs` - SockJS fallback (폴링, 롱폴링 등 자동 전환)

**구독 경로**:
- `/topic/auctions/{auctionId}` - 특정 경매의 실시간 이벤트 수신

### 9.4 메시지 발행

**AuctionWebSocketPublisher.java** (`auction/auction/infra/websocket/AuctionWebSocketPublisher.java`)

```java
@Component
@RequiredArgsConstructor
public class AuctionWebSocketPublisher {

    private final SimpMessagingTemplate messagingTemplate;

    /** 입찰 발생 메시지 브로드캐스트 */
    public void publishBid(String auctionId, Long currentBid, Integer bidCount, Long bidderId) {
        AuctionWebSocketMessage message = AuctionWebSocketMessage.bid(currentBid, bidCount, bidderId);
        String destination = "/topic/auctions/" + auctionId;
        messagingTemplate.convertAndSend(destination, message);
    }

    /** 경매 종료 (낙찰) 메시지 브로드캐스트 */
    public void publishEnded(String auctionId, Long winnerId, Long finalBid) {
        AuctionWebSocketMessage message = AuctionWebSocketMessage.ended(winnerId, finalBid);
        String destination = "/topic/auctions/" + auctionId;
        messagingTemplate.convertAndSend(destination, message);
    }

    /** 경매 종료 (유찰) 메시지 브로드캐스트 */
    public void publishUnsold(String auctionId) {
        AuctionWebSocketMessage message = AuctionWebSocketMessage.unsold();
        String destination = "/topic/auctions/" + auctionId;
        messagingTemplate.convertAndSend(destination, message);
    }
}
```

   └─> POST /api/v1/auctions/A-TEST01/bids { amount: 740000 }
   └─> BidService: 입찰 처리 + DB 저장
   └─> WebSocketPublisher.publishBid()
        └─> /topic/auctions/A-TEST01 → BID 메시지

4. Client A, B: WebSocket 메시지 수신
   └─> 화면 갱신 (현재가: 740,000원, 입찰 수: 7회)

5. Client B: 재입찰 (750,000원)
   └─> POST /api/v1/auctions/A-TEST01/bids { amount: 750000 }
   └─> WebSocketPublisher.publishBid()
        └─> /topic/auctions/A-TEST01 → BID 메시지

6. Client A, B: WebSocket 메시지 수신
   └─> 화면 갱신 (현재가: 750,000원, 입찰 수: 8회)
   └─> Client A: "경쟁에서 밀렸습니다" 알림 표시
```

#### 경매 종료 시나리오

```
1. AuctionCloseScheduler: 1초마다 만료 경매 확인
   └─> ends_at <= NOW() AND status = 'LIVE'

2. 경매 A-TEST01 만료 감지
   └─> 최고 입찰 조회 (Client B, 750,000원)
   └─> auction.close(winnerId=B, finalBid=750000)
   └─> WebSocketPublisher.publishEnded()
        └─> /topic/auctions/A-TEST01 → ENDED 메시지

3. Client A, B: WebSocket 메시지 수신
   └─> Client A: "경매가 종료되었습니다. 낙찰자: B" 표시
   └─> Client B: "축하합니다! 낙찰되었습니다. 결제 기한: 24시간" 표시

4. Outbox 저장
   └─> topic: auction.ended
   └─> payload: { auctionId, winnerId, finalBid, ... }

5. OutboxRelayScheduler: 5초 후 Kafka 발행
   └─> Order Service: 주문 자동 생성
```

### 9.7 구독자 범위 및 메시지 수신 대상

| 메시지 타입 | 구독 경로 | 수신 대상 | 용도 |
|-----------|----------|---------|------|
| BID | `/topic/auctions/{auctionId}` | 해당 경매를 구독 중인 모든 클라이언트 | 현재가 갱신, 입찰 경쟁 알림 |
| ENDED (낙찰) | `/topic/auctions/{auctionId}` | 해당 경매를 구독 중인 모든 클라이언트 | 경매 종료 알림, 낙찰자 안내 |
| ENDED (유찰) | `/topic/auctions/{auctionId}` | 해당 경매를 구독 중인 모든 클라이언트 | 경매 종료 알림, 유찰 안내 |

**특징**:
- 경매별 독립된 토픽으로 구독 → 다른 경매의 이벤트와 격리
- 브로드캐스트 방식 → 구독자 모두에게 동일한 메시지 전달
- 페이지를 벗어나면 자동 연결 해제 → 불필요한 메시지 수신 없음

### 9.8 에러 처리 및 재연결

#### 연결 실패 시

```javascript
stompClient.connect({}, onConnected, onError);

function onError(error) {
    console.error('WebSocket 연결 실패:', error);

        console.log('재연결 시도...');

socket.onclose = function(event) {

### 9.9 보안 및 제약사항

| 항목 | 현재 상태 | 향후 개선 |
|------|----------|---------|
| **인증** | 미적용 (누구나 구독 가능) | JWT 기반 인증 추가 예정 |
| **인가** | 미적용 (모든 경매 구독 가능) | 비공개 경매 구독 권한 검증 |
| **Rate Limiting** | 미적용 | 구독 요청 수 제한 (DoS 방지) |
| **CORS** | `*` 전체 허용 | 프로덕션: 특정 도메인만 허용 |
| **메시지 크기** | 제한 없음 | 최대 크기 설정 (예: 10KB) |
| **구독자 수** | 제한 없음 | 경매별 최대 구독자 수 제한 고려 |

**보안 개선 예시** (향후):

```java
@Override
public void configureClientInboundChannel(ChannelRegistration registration) {
    registration.interceptors(new ChannelInterceptor() {
        @Override
        public Message<?> preSend(Message<?> message, MessageChannel channel) {
            StompHeaderAccessor accessor = StompHeaderAccessor.wrap(message);

            if (StompCommand.SUBSCRIBE.equals(accessor.getCommand())) {
                String destination = accessor.getDestination();
                String jwtToken = accessor.getFirstNativeHeader("Authorization");

                // JWT 검증 + 구독 권한 확인
                if (!hasPermission(jwtToken, destination)) {
                    throw new AccessDeniedException("구독 권한이 없습니다.");
                }
            }

            return message;
        }
    });
}
```

### 9.10 모니터링

#### 연결 수 확인

```java
@Component
public class WebSocketEventListener {

    private final AtomicInteger connectionCount = new AtomicInteger(0);

    @EventListener
    public void handleWebSocketConnectListener(SessionConnectEvent event) {
        connectionCount.incrementAndGet();
        log.info("New WebSocket connection. Total: {}", connectionCount.get());
    }

    @EventListener
    public void handleWebSocketDisconnectListener(SessionDisconnectEvent event) {
        connectionCount.decrementAndGet();
        log.info("WebSocket connection closed. Total: {}", connectionCount.get());
    }
}
```
