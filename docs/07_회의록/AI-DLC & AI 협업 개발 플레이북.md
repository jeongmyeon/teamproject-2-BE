# AI-DLC & AI 협업 개발 플레이북

> 팀 내부 공유용 가이드 · 작성 기준일: 2026-07-02
> 목적: AI-DLC 방법론과 역할 기반 프롬프트 패턴을 결합해, "메모리(컨텍스트)를 먼저 세팅하고 점진적으로 진행"하는 개발 방식을 표준화한다.

## 0. 이 문서의 층위 구분 (먼저 읽을 것)

혼동을 막기 위해 세 가지 개념을 분리한다.

| 층위 | 이름 | 정체 | 역할 |
|---|---|---|---|
| 방법론 | **AI-DLC** | 개발 생애주기 프로세스 | *언제·어떤 순서로* 일할지 |
| 운영 원칙 | **컨텍스트 우선 + 점진적 진행** | 협업 규칙 | *어떻게* AI와 일할지 |
| 실행 기법 | **역할 기반 프롬프트 8패턴** | 프롬프트 템플릿 | *무엇을* 시킬지 |

> **[Fact]** 질문에 나열된 "풀스택 개발 / 리팩토링 / 디버깅 / 시스템 설계 …" 8개는 방법론이 아니라 **프롬프트 패턴(persona prompting)** 이다.
> **[Opinion]** 세 층위를 명확히 나눠 문서화하면, 팀원이 "AI-DLC = 프롬프트 몇 개"라고 오해하는 것을 막을 수 있다.

## 1. AI-DLC란 무엇인가

### 1.1 정의

**AI-DLC (AI-Driven Development Lifecycle)** 는 기존 SDLC(Software Development Lifecycle)를 AI가 주 실행 주체가 되도록 재편한 개발 방법론이다. 인간은 방향 설정·의사결정·검증을 담당하고, AI가 설계·구현·문서화 등 실행 부담을 진다.

> **[검증 필요]** AI-DLC는 AWS가 제안한 것으로 알려진 비교적 최신 개념이다. 세부 단계 명칭(예: Inception / Construction / Operations)과 하위 개념(Mob, Bolt 등)은 자료마다 표기가 다를 수 있으므로, 팀 표준으로 채택하기 전 **AWS 공식 문서로 원문 용어를 확인**할 것. 본 문서는 실무 적용 관점의 요약이며 공식 스펙 인용이 아니다.

### 1.2 기존 SDLC와의 대비 (개념 비교)

| 관점 | 전통적 SDLC | AI-DLC |
|---|---|---|
| 주 실행 주체 | 사람 | AI (사람은 감독·검증) |
| 진행 단위 | 스프린트(주 단위) | 짧은 시간박스(시간~일 단위) |
| 산출물 생성 | 사람이 작성 | AI가 초안 → 사람이 승인 |
| 인간의 병목 | 구현 속도 | 의사결정·리뷰 속도 |

> **[Opinion]** AI-DLC의 핵심 이동은 "인간이 코드를 짜는 병목" → "인간이 결정·검증하는 병목"으로 병목의 위치가 바뀐다는 점이다. 따라서 팀 역량의 초점도 *구현 스킬*에서 *요구사항 정의·리뷰·아키텍처 판단*으로 옮겨간다.

### 1.3 AI-DLC의 통상적 3단계 (요약)

1. **Inception (구상)** — 요구사항을 AI와 함께 구조화하고, 모호함을 질문으로 좁힌다.
2. **Construction (구축)** — 설계 → 구현 → 테스트를 짧은 단위로 반복한다.
3. **Operations (운영)** — 배포·모니터링·개선을 AI 지원으로 수행한다.

> **[검증 필요]** 위 3단계 명칭은 통용되는 요약이며, 공식 명칭과 세부 프로세스는 원문 확인이 필요하다.

## 2. 핵심 운영 원칙: "컨텍스트 우선 + 점진적 진행"

이 문서에서 가장 실무 가치가 높은 부분이다. 8개 프롬프트 패턴을 아무리 잘 써도, 이 원칙 없이는 결과 품질이 흔들린다.

### 2.1 원칙 A — 역할·규칙을 "먼저, 지속적으로" 준다

AI에게 매번 역할과 규칙을 반복 입력하지 말고, **영속 컨텍스트(persistent context)** 에 한 번 심어 둔다.

- **프로젝트 규칙 파일** (예: `CLAUDE.md`, 저장소 루트) — 기술 스택, 코딩 컨벤션, 금지 사항, 아키텍처 원칙을 명시
- **역할 선언** — "너는 시니어 백엔드 엔지니어다. Java 17+ 문법(record/sealed/pattern matching) 우선, SOLID·DRY·YAGNI 준수" 같은 지시를 상단에 고정
- **제약 명시** — 출력 형식, 파일 위치, 테스트 필수 여부 등

> **[Fact]** 역할·제약을 대화 초반(또는 영속 메모리)에 고정하면 이후 모든 응답이 그 컨텍스트를 상속한다. 매 프롬프트에 재입력하는 것보다 일관성이 높고 토큰 낭비가 적다.

**예시 — 프로젝트 규칙 파일 스켈레톤**

```markdown
# 프로젝트 규칙 (CLAUDE.md)

## 역할
너는 이 저장소의 시니어 백엔드 엔지니어다.

## 기술 스택
- Java 17+, Spring Boot 3.x, Spring Data JPA, Gradle

## 코딩 원칙
- SOLID, DRY, YAGNI, 12-Factor 준수
- record / sealed / pattern matching 우선
- 도메인 계층은 프레임워크에 의존하지 않는다 (클린 아키텍처)

## 금지
- 검증 없는 라이브러리 추천 금지 (근거: 벤치마크/공식문서 필수)
- 광범위한 일괄 수정 금지 (변경은 작은 단위로)

## 출력 규칙
- 코드 변경 시 영향받는 파일 목록을 먼저 제시
- 테스트 코드 동반
```

### 2.2 원칙 B — "점진적으로(incrementally)" 진행한다

큰 작업을 한 번에(one-shot) 시키지 말고, 작은 단위로 쪼개 각 단계를 검증하며 나아간다. 이는 AI-DLC의 "짧은 시간박스" 개념과 직접 연결된다.

**점진 진행 루프**

```
1) 범위 좁히기   → 이번에 할 한 가지 작업만 정의
2) 계획 요청     → AI에게 접근 방식을 먼저 말하게 함 (코드 X)
3) 검토·승인     → 계획의 전제·엣지케이스 확인
4) 구현          → 승인된 범위만 구현
5) 검증          → 테스트·리뷰
6) 반복          → 다음 단위로
```

> **[Opinion]** 3번(계획을 먼저 말하게 하기)을 건너뛰면, 잘못된 전제 위에 완성된 코드가 나와 되돌리는 비용이 커진다. "구현 전 계획 승인"은 점진 진행의 안전장치다.

> **[Fact]** 작업 단위가 작을수록 (a) AI의 컨텍스트 이탈 확률이 낮고 (b) 리뷰 부담이 분산되며 (c) 롤백 범위가 작다.

### 2.3 두 원칙의 결합

```
[영속 컨텍스트: 역할·규칙 고정]  ← 원칙 A (한 번 세팅)
            │
            ▼
[작업1] 계획→승인→구현→검증  ← 원칙 B (반복)
[작업2] 계획→승인→구현→검증
[작업3] ...
```

## 3. 역할 기반 프롬프트 8패턴 (실행 기법)

각 패턴은 "AI에게 어떤 시니어 페르소나를 부여하고 어떤 산출물을 받을지"를 규격화한 것이다. 모든 패턴은 **2장의 영속 컨텍스트를 상속**한다는 전제로 사용한다.

### 패턴 1 — 처음부터 완전한 애플리케이션 개발

- **페르소나**: 고급 풀스택 엔지니어
- **접근**: 아키텍처 설계 → 최소하지만 확장 가능한 버전 구현
- **산출물**: 아키텍처 · 파일 구조 · DB 스키마 · API 엔드포인트 · UI 아키텍처 · 전체 코드
- **원칙**: 실제 스타트업 MVP처럼, 확장 가능하게
- **적용 시점**: AI-DLC의 Inception → Construction 초반

### 패턴 2 — 코드베이스 이해 및 리팩토링

- **페르소나**: 대규모 낯선 코드베이스에 막 합류한 시니어
- **접근**: 아키텍처·데이터 흐름 파악 → 문제 식별 → 리팩토링
- **식별 대상**: 구조적 문제 · 중복 코드 · 성능 병목 · 유지보수성 리스크
- **산출물**: 아키텍처 요약 · 문제 영역 · 리팩토링 전략 · 개선된 코드
- **불변 조건**: **기능은 변경되지 않음, 품질만 향상**

### 패턴 3 — 시니어 디버깅 엔지니어

- **페르소나**: 프로덕션 버그 조사자
- **접근**: 신중한 분석 → 단계별 사고 → 근본 원인(root cause) → 견고한 해결책
- **산출물**: 코드 기능 설명 · 문제점 · 실패 원인 · 엣지 케이스 · 수정된 프로덕션 준비 코드
- **적용 시점**: AI-DLC의 Operations

### 패턴 4 — 시스템 설계 + 구현

- **페르소나**: 시니어 시스템 아키텍트
- **접근**: 확장 가능한 시스템 설계 → 최소 실행 버전 구현
- **산출물**: 아키텍처 · 컴포넌트 구조 · 데이터 흐름 · API 설계 · DB 스키마 · 캐싱 전략 · 구현 코드
- **패턴 1과 차이**: 1은 "제품 전체", 4는 "특정 시스템/기능의 설계 깊이"에 집중

### 패턴 5 — 성능 최적화

- **페르소나**: 성능 엔지니어
- **목표**: 속도 · 메모리 · 확장성
- **탐지 대상**: 병목 · 비효율 로직 · 불필요한 렌더링
- **산출물**: 성능 문제 · 최적화 전략 · 개선된 코드
- **주의**: 최적화는 **측정 후 진행**. 근거 없는 추측성 최적화 금지

> **[Fact]** 최적화의 대원칙은 "측정하지 않은 것을 최적화하지 말라". 프로파일링/벤치마크로 병목을 먼저 확정한다.

### 패턴 6 — 클린 아키텍처 재구축

- **페르소나**: 시니어 엔지니어
- **접근**: 관심사 분리 · 모듈성 향상 · 결합도 감소
- **산출물**: 새 폴더 구조 · 아키텍처 설명 · 리팩토링된 코드
- **불변 조건**: **동작은 변경되지 않음, 구조만 개선**
- **패턴 2와 차이**: 2는 "문제 진단 중심", 6은 "클린 아키텍처 형태로의 구조 변환"

### 패턴 7 — 다중 에이전트 워크플로우

- **구성**: 4개 협력 에이전트를 한 세션에서 역할 분담
    - **Architect** → 시스템 설계
    - **Engineer** → 개발
    - **Reviewer** → 품질 관리
    - **Optimizer** → 성능 개선
- **산출물**: 아키텍처 · 구현 · 검토 피드백 · 최종 최적화 버전
- **적용 시점**: 규모 있는 기능을 한 흐름에서 설계~최적화까지 통합할 때

> **[Opinion]** 패턴 7은 앞선 1·3·5·6을 순차 파이프라인으로 묶은 상위 패턴이다. 단, 한 세션에 4역할을 몰면 각 단계 검증(원칙 B)이 느슨해질 수 있으니, 에이전트 간 인수인계 지점마다 사람이 승인하는 게 안전하다.

### 패턴 8 — 프로덕션 레벨 UI 컴포넌트 빌더

- **페르소나**: 시니어 프론트엔드 엔지니어
- **접근**: 재사용 가능 · 접근성 준수 · 프로덕션 준비
- **고려사항**: 로딩 상태 · 엣지 케이스 · 반응형 · 접근성(a11y)
- **산출물**: 컴포넌트 아키텍처 · Props 설계 · 구현 · 사용 예시

## 4. 패턴 ↔ AI-DLC 단계 매핑

| AI-DLC 단계 | 주로 쓰는 패턴 |
|---|---|
| Inception (구상) | 1, 4 (설계·요구사항 구조화) |
| Construction (구축) | 1, 4, 8, 7 (구현) |
| Construction (품질) | 2, 6 (리팩토링·구조 개선) |
| Operations (운영) | 3, 5 (디버깅·최적화) |

> **[Opinion]** 이 매핑은 절대 규칙이 아니라 시작점이다. 실제로는 한 작업 안에서 여러 패턴을 오간다(예: 디버깅 3 → 최적화 5 → 클린화 6).

## 5. 실전 통합 워크플로우 (예시)

신규 기능 "주문 취소 API" 개발을 가정한 흐름.

```
[0] 영속 컨텍스트 세팅 (원칙 A)
    → CLAUDE.md에 역할·스택·컨벤션 고정

[1] Inception (패턴 4 + 원칙 B)
    → "설계만. 코드 X" 로 API·스키마·데이터 흐름 초안 요청
    → 전제·엣지케이스(부분 취소, 이미 배송됨 등) 검토·승인

[2] Construction (패턴 1/4 + 원칙 B)
    → 승인된 설계 범위만 구현 요청
    → 도메인 → 애플리케이션 → 인프라 순 작은 단위로

[3] 품질 (패턴 6/2)
    → 클린 아키텍처 형태 점검, 결합도 확인

[4] 검증 (패턴 3)
    → 실패 시나리오·엣지케이스 테스트

[5] Operations (패턴 5)
    → 필요 시 쿼리/캐싱 최적화 (측정 후)
```

## 6. 팀 적용 체크리스트

- [ ] 저장소 루트에 **프로젝트 규칙 파일**(역할·스택·컨벤션·금지)이 있는가
- [ ] 작업을 시작할 때 **한 가지 단위**로 범위를 좁혔는가
- [ ] 구현 전에 AI에게 **계획을 먼저 말하게** 했는가 (원칙 B-3)
- [ ] 리팩토링/클린화 작업에서 **"기능·동작 불변"** 조건을 명시했는가 (패턴 2·6)
- [ ] 최적화 전에 **측정/프로파일링**을 했는가 (패턴 5)
- [ ] AI가 인용한 라이브러리·수치에 **근거(벤치/공식문서) 요구**를 했는가
- [ ] 다중 에이전트(패턴 7) 사용 시 **인수인계 지점마다 사람 승인**이 있는가
- [ ] AI-DLC 세부 용어를 팀 표준으로 쓰기 전 **공식 문서로 검증**했는가

## 7. 한계와 주의 (정직한 고지)
