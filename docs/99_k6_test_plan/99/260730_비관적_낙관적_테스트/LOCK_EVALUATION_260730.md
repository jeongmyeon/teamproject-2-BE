# 260730 경매 낙관적 락·비관적 락 중간 평가

작성일: 2026-07-30 (Asia/Seoul)

## 1. 결론 요약

현재 동일 조건의 15초 Smoke 1회씩을 비교하면 **두 락 모두 데이터 정합성과 안정성 기준을 통과**했다.

- 두 방식 모두 성공률 50%, 예상 밖 오류 0%, 409/429/5xx 0건이었다.
- 두 방식 모두 `k6 성공 수 = bidCount 증가량`이 경매 A/B 각각 정확히 일치했다.
- 낙관적 락은 비관적 락보다 입찰 평균 지연이 13.2%, p95가 14.0% 낮았다.
- 비관적 락은 15초 동안 완료한 입찰 흐름이 4건 많아 흐름 처리율이 2.9% 높았다.
- p99는 비관적 락이 1.6% 낮아 사실상 비슷한 범위였다.

따라서 이번 Smoke만으로 어느 방식이 더 빠르다고 확정할 수 없다. **현재 판단은 기능·정합성은 동등, 지연시간 중앙 구간은 낙관적 락이 소폭 유리, 처리량과 tail latency는 유의미한 차이가 확인되지 않음**이다.

최종 선택을 위해서는 비관적 락 2분 본 테스트와 각 방식 최소 3회 반복 결과가 필요하다.

## 2. 비교 조건

| 항목 | 낙관적 락 | 비관적 락 |
|---|---|---|
| AWS API | 동일 | 동일 |
| Auction replica | 3 | 3 |
| 경매 | 신규 경매 2개 | 별도 신규 경매 2개 |
| 최초 bidCount | A/B 모두 0 | A/B 모두 0 |
| 최소 증가액 | A/B 모두 500원 | A/B 모두 500원 |
| 입찰자 | 사용자 2·3 | 사용자 2·3 |
| 경매별 VU | 2 | 2 |

서로 다른 시각과 서로 다른 경매 데이터로 실행했으므로 네트워크·클러스터 순간 상태의 영향을 완전히 제거한 실험은 아니다.

## 4. 데이터 정합성 평가

### 낙관적 락

| 상품 | k6 성공 | bidCount 증가 | 가격 증가 | 판정 |
|---|---:|---:|---:|---|
| A | 22 | 22 | `22 × 500원` | PASS |
| B | 24 | 24 | `24 × 500원` | PASS |

### 비관적 락

| 상품 | k6 성공 | bidCount 증가 | 가격 증가 | 판정 |
|---|---:|---:|---:|---|
| A | 24 | 24 | `24 × 500원` | PASS |
| B | 24 | 24 | `24 × 500원` | PASS |

두 방식 모두 API 성공 응답과 최종 경매 상태가 일치했다. 현재 k6 결과만으로는 Bid 테이블의 실제 행 수와 `MAX(amount)`, 비관적 실행의 version delta를 직접 조회하지 못했으므로 최종 평가에는 DB 조회 결과를 추가해야 한다.

## 5. 성공률 50%의 의미

이번 시나리오는 각 경매에서 두 VU가 거의 동시에 같은 현재가를 조회한 뒤 같은 금액을 보낸다. 먼저 처리된 한 요청은 성공하고, 나중 요청은 최신 최소 입찰가 검증에서 400/422로 거절된다.

따라서 성공률 50%는 장애나 락 실패가 아니라 현재 `refresh` 입력 패턴의 정상 결과다. 이 수치만으로 낙관적·비관적 락의 우열을 평가하면 안 된다.

낙관적 락의 409가 0건이라는 사실도 충돌이 전혀 없었다는 뜻은 아니다. 내부 재시도가 충돌을 회복했거나, 한 요청의 커밋 이후 다른 요청이 업무 검증에서 먼저 거절됐을 수 있다. 실제 충돌과 재시도 수는 서버 메트릭으로 확인해야 한다.

## 6. 방식별 평가

### 6.1 낙관적 락

장점:

- DB 행 락 대기 없이 충돌 시 재시도하므로 여러 경매로 트래픽이 분산되는 환경에 유리하다.
- replica 확장 시 DB connection이 lock wait에 묶이는 위험이 상대적으로 낮다.
- 이번 Smoke에서 평균과 p95가 비관적 락보다 낮았다.
- 100 VU 로컬 P0 테스트에서도 재시도 소진 없이 정합성을 유지한 기존 근거가 있다.

주의점:

- 같은 인기 경매에 충돌이 집중되면 재시도 횟수만큼 DB 작업이 증폭된다.
- 최대 3회 재시도 후 409가 발생할 수 있다.
- 충돌, 재시도 성공/실패, 회복 시간을 반드시 계측해야 한다.
- 구현과 예외 분류가 비관적 락보다 복잡하다.

### 6.2 비관적 락

장점:

- 동일 경매 입찰을 DB에서 직렬화하므로 처리 순서와 정합성 모델이 단순하다.
- 애플리케이션 재시도 없이 최신 행을 확보한 상태에서 검증한다.
- 이번 Smoke에서 409·5xx·deadlock 징후 없이 두 경매가 균등하게 처리됐다.
- p99와 최대 지연은 낙관적 Smoke보다 소폭 낮았다.

주의점:

- 경쟁 요청은 DB row lock을 기다리는 동안 connection과 transaction을 점유한다.
- 인기 경매 집중도가 높아지면 p95/p99, Hikari pending, DB lock wait가 급격히 증가할 수 있다.
- deadlock, lock timeout, connection pool 고갈을 별도로 감시해야 한다.
- 이번 Smoke 평균과 p95는 낙관적 락보다 약 13~14% 높았다.

## 7. 현재 단계의 선택 제안

| 운영 상황 | 우선 검토 방식 | 이유 |
|---|---|---|
| 여러 경매로 트래픽 분산, 충돌 낮음·중간 | 낙관적 락 | DB lock wait 감소와 수평 확장 친화성 |
| 소수 인기 경매에 집중, 충돌 높음, 처리 직렬화 우선 | 비관적 락 | 단순하고 명확한 동일 행 직렬화 |
| DB connection 여유가 작음 | 낙관적 락 | lock wait 중 connection 점유 위험 회피 |
| 재시도 증폭이 병목 | 비관적 락 또는 경매별 큐 | 반복 DB 작업 억제 |
| 극단적인 hotspot | 두 방식만으로 결정 금지 | 경매별 명령 큐/단일 writer까지 검토 |

현재 서비스의 기본 선택은 **낙관적 락 유지가 합리적**이다. 다만 이는 Smoke에서 압도적 성능 우위가 증명됐기 때문이 아니라, 여러 Auction replica와 다수 경매로 분산되는 일반 운영 모델에서 DB lock wait를 줄일 수 있다는 구조적 판단이다. 인기 경매 hotspot이 주 트래픽이라면 비관적 락 또는 경매별 직렬 큐를 다시 검토한다.

## 8. 최종 판정을 위해 남은 측정

1. 현재 비관적 배포에서 동일 경매 A/B로 2분 본 테스트 실행
2. 비관적 `2xx = bidCount delta = Bid row delta` DB 확인
3. 비관적 version delta 0 확인
4. PostgreSQL lock wait, blocked query, deadlock 확인
5. Hikari active/idle/pending/timeout 확인
6. pod별 요청 수, CPU, memory, restart 확인
7. 낙관적·비관적 동일 프로필을 각각 최소 3회 실행해 중앙값과 범위 비교

현재 보유한 낙관적 2분 결과는 758회 시도, 379회 성공, p95 723.57ms, p99 957.57ms다. 이에 대응하는 비관적 2분 결과가 생기기 전까지 본 테스트 성능 비교는 보류한다.
