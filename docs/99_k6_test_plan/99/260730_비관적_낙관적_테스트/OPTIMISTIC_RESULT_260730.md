## 1차 판정

- PASS: `bidCount 증가량 = k6 2xx 성공 수`가 두 상품 모두 정확히 일치
- PASS: 예상 밖 오류, 인증 오류, 5xx, 429, 상세 조회 오류가 관찰되지 않음
- PASS: p95 723.57 ms로 설정 임계값 2초 이내
- PASS: 상품 A/B 시도 및 성공 수 편차가 매우 작아 두 상품이 균형 있게 처리됨
- 확인 필요: HTTP 409는 0건이고 동시 동일 금액의 절반이 400/422로 거절됨. 실제 낙관적 락 충돌/재시도 횟수는 서버 로그와 메트릭에서 별도 확인해야 함
- 확인 필요: pod별 요청 분배, CPU/memory, DB lock wait, connection pool 수치는 이번 k6 결과만으로 확인할 수 없음

현재 입력 패턴에서는 두 사용자가 같은 현재가를 읽고 같은 금액을 전송하므로 성공률 50%와 업무 거절 50%는 자연스러운 결과다. 성능 비교에서는 비관적 락도 동일한 smoke 15초 + load 2분 순서로 실행해야 한다.

## 비관적 락 비교 전 준비

1. 동일한 시작가·최소 증가액·종료시간을 가진 새 경매 2개 생성
2. 비관적 락 배포 및 Auction pod Ready 3/3 확인
3. pod restart, HPA, resource limit, DB pool을 낙관적 실행과 동일하게 유지
4. `test.local.env`의 두 경매 ID 교체
5. 입찰자 계정 파일을 다시 생성하고 같은 15초 smoke + 2분 load 실행
6. 두 JSON을 `compare-results.mjs`로 비교
