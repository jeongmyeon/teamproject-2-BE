## 1. 현재 시스템 주요 이슈

### 1.1 JWT 인증 강결합 문제 ⚠️ 높음

#### 문제점

**각 서비스에 JWT 검증 로직이 중복 구현되어 강하게 결합**되어 있습니다.

| 문제 유형 | 영향도 | 현황 |
|---------|-------|------|
| 코드 중복 | 높음 | JwtTokenProvider가 4개 서비스(auction, member, apigateway, payment)에 각각 구현 |
| 필터 불일치 | 중간 | HeaderAuthenticationFilter가 3가지 버전으로 분리 (auction, common, order) |
| 의존성 중복 | 중간 | jjwt 라이브러리가 4개 서비스에 중복 선언 |
| 유지보수 비용 | 높음 | JWT 알고리즘 변경 시 모든 서비스 수정 필요 |

#### 구체적 사례

```java
// auction/HeaderAuthenticationFilter.java (36 lines)
// - Gateway 헤더 + Bearer 토큰 둘 다 처리
// - JwtTokenProvider 의존

// common/HeaderAuthenticationFilter.java (15 lines)
// - Gateway 헤더만 처리
// - JwtTokenProvider 불필요

// order/OrderHeaderAuthenticationFilter.java (20 lines)
// - Gateway 헤더만 처리
// - null/undefined 검증 추가
// - 기본 role 처리 로직
```

**각 서비스마다 다른 인증 로직을 사용하여 일관성이 결여**되어 있습니다.

#### 개선 방안

```
[AS-IS]
Client → API Gateway (JWT 검증) → 각 서비스 (JWT 재검증)
                                    ↓
                          중복 검증 + 강결합

[TO-BE]
Client → API Gateway (JWT 검증) → 각 서비스 (헤더만 신뢰)
              ↓                      ↓
         X-Member-Id           common 모듈의
         X-Member-Role         단일 Filter 사용
```

**구현 단계:**

1. **Phase 1**: API Gateway에서 JWT 검증 집중화
   - Gateway가 JWT 검증 후 `X-Member-Id`, `X-Member-Role` 헤더로 전달
   - 내부 서비스는 Gateway를 신뢰 (헤더 기반 인증만 수행)

2. **Phase 2**: Common 모듈에 인증 로직 통합
   - `HeaderAuthenticationFilter`를 common에 단일 버전으로 통합
   - 모든 서비스가 common 모듈의 필터 사용

3. **Phase 3**: 각 서비스에서 JWT 의존성 제거
   - Member, API Gateway만 JWT 라이브러리 필요
   - 나머지 서비스는 헤더 기반 인증만 사용

**효과:**
- 보안 취약점 패치 시 Gateway만 업데이트
- 테스트 단순화 (각 서비스는 헤더만 모킹)
- 코드 중복 제거 (~200 lines 절감)

```java
// auction/SecurityConfig.java
config.setAllowedOriginPatterns(List.of("http://localhost:*", "http://127.0.0.1:*", "https://*.vercel.app"));
config.setAllowedOrigins(List.of("https://biddy-zeta.vercel.app", "http://biddy-zeta.vercel.app"));
```

## 2. 필수 인프라 구성요소 부족

### 2.1 모니터링 스택 미구축 ⚠️ 긴급

현재 k8s-aws/monitoring/에 Prometheus, Grafana 매니페스트는 있지만 **실제 메트릭 수집 및 대시보드가 구성되지 않음**.

#### 부족한 요소

| 구성요소 | 현황 | 필요성 | 우선순위 |
|---------|------|--------|---------|
| **Prometheus** | YAML만 존재 | 메트릭 수집/저장 | 긴급 |
| **Grafana** | YAML만 존재 | 시각화 대시보드 | 긴급 |
| **AlertManager** | 없음 | 장애 알림 (Slack/Email) | 높음 |
| **Service Metrics** | 일부 actuator만 | 비즈니스 메트릭 수집 | 높음 |

#### 필수 메트릭

**인프라 메트릭:**
- CPU/메모리 사용률
- 디스크 I/O
- 네트워크 트래픽
- Pod 재시작 횟수

**애플리케이션 메트릭:**
- HTTP 요청 수/응답 시간 (P50, P95, P99)
- 에러율 (4xx, 5xx)
- Database 연결 풀 상태
- Kafka 메시지 처리 지연

**비즈니스 메트릭:**
- 실시간 경매 수
- 분당 입찰 수
- 낙찰률
- 결제 성공/실패율
- 평균 거래 금액

#### Grafana 대시보드 구성안

```
[Dashboard 1] 시스템 개요
- 전체 서비스 상태 (UP/DOWN)
- CPU/메모리 사용률
- 초당 요청 수 (RPS)
- 평균 응답 시간

[Dashboard 2] 경매 비즈니스 메트릭
- 실시간 경매 수 (LIVE, ENDED)
- 분당 입찰 수 (실시간 그래프)
- 낙찰률 추이
- 인기 카테고리 TOP 10

[Dashboard 3] 에러 추적
- 서비스별 에러율
- 5xx 에러 상세 (스택 트레이스)
- Kafka 메시지 실패율

[Dashboard 4] 성능 분석
- API 응답 시간 (P50/P95/P99)
- Database 쿼리 성능
- 캐시 히트율 (Redis)
```

### 2.2 분산 추적(Distributed Tracing) 부재 ⚠️ 높음

MSA 환경에서 요청이 여러 서비스를 거쳐가는데, **요청 흐름을 추적할 수단이 없음**.

#### 필요성

```
예시 시나리오: 입찰 요청이 느린 경우

Client → API Gateway → Auction → Member (예치금 확인)
                           ↓
                         Kafka → Order (낙찰 시)

어느 구간에서 지연이 발생했는지 알 수 없음!
```

#### 도입 기술: Zipkin 또는 Jaeger

**Spring Cloud Sleuth + Zipkin 구성:**

```yaml
# application.yml (모든 서비스)
spring:
  sleuth:
    sampler:
      probability: 0.1  # 10% 샘플링
  zipkin:
    base-url: http://zipkin:9411
```

**Trace ID로 전체 요청 흐름 추적:**
```
Trace ID: abc123
  Span 1: API Gateway (5ms)
  Span 2: Auction Service (120ms) ← 병목!
  Span 3: Member Service (8ms)
  Span 4: Kafka Publish (2ms)
```

### 2.3 중앙 로깅 시스템 부재 ⚠️ 높음

각 서비스의 로그가 분산되어 있어 **문제 진단이 어려움**.

#### 현재 문제

- 각 서비스 Pod에 로그가 분산
- Pod 재시작 시 로그 유실
- 여러 서비스를 넘나드는 요청 추적 불가

#### 필요 구성: ELK/EFK Stack

**Option A: ELK Stack**
```
Elasticsearch ← Logstash ← Filebeat (각 Pod)
     ↓
   Kibana (시각화)
```

**Option B: EFK Stack (Kubernetes 친화적)**
```
Elasticsearch ← Fluentd (DaemonSet) ← 각 Pod 로그
     ↓
   Kibana
```

**로그 수집 항목:**
- Application 로그 (ERROR, WARN, INFO)
- Access 로그 (API 요청/응답)
- Audit 로그 (회원 인증, 결제 등 민감 작업)
- Kafka 메시지 처리 로그

**Kibana 대시보드:**
- 실시간 에러 로그 모니터링
- 특정 사용자/경매 ID로 로그 필터링
- 시간대별 로그 분포

### 2.4 헬스체크 및 Readiness/Liveness Probe 미흡

현재 Kubernetes 매니페스트에 Probe 설정이 **부족하거나 불완전**합니다.

#### 필요한 Probe 구성

```yaml
# auction-service deployment
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8084
  initialDelaySeconds: 60
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8084
  initialDelaySeconds: 30
  periodSeconds: 5

# 의존성 체크 (DB, Kafka, Redis)
management:
  health:
    livenessState:
      enabled: true
    readinessState:
      enabled: true
  endpoint:
    health:
      probes:
        enabled: true
      show-details: always
```

### 2.6 Rate Limiting 및 Circuit Breaker 부재

#### Rate Limiting (API Gateway)

현재 무제한 요청 허용 → **DDoS 취약**

```yaml
# API Gateway에 Resilience4j RateLimiter 적용
resilience4j.ratelimiter:
  instances:
    auction-api:
      limitForPeriod: 100      # 10초당 100 요청
      limitRefreshPeriod: 10s
      timeoutDuration: 0s
```

#### Circuit Breaker

서비스 장애 전파 방지

```java
// Member Service 호출 시 Circuit Breaker
@CircuitBreaker(name = "memberService", fallbackMethod = "memberFallback")
public MemberInfo getMemberInfo(Long memberId) {
    // Member Service 호출
}

private MemberInfo memberFallback(Long memberId, Exception e) {
    // 캐시된 정보 반환 또는 기본값
    return MemberInfo.unknown(memberId);
}
```

## 3. 희귀물건 중고거래 특화 기능 제안

### 3.1 감정/검증 시스템 ⭐ 핵심 차별화

희귀 물건은 **진위 여부가 가장 중요**합니다.

#### 기능 설계

**3.1.1 전문가 감정 요청**

```
상품 등록 시:
1. 판매자가 "감정 요청" 선택
2. 상품 사진 + 증빙서류 업로드
3. 감정료 결제 (예: 5만원)
4. 전문 감정사에게 배정

감정사 검토:
- 사진 검토 (진품/위조 판단)
- 상태 등급 평가 (A+, A, B, C)
- 감정서 발급

결과:
- 상품에 "감정 완료" 배지 표시
- 감정서 PDF 첨부
- 신뢰도 상승 → 낙찰가 향상
```

**DB 설계:**

```sql
-- 감정 요청
CREATE TABLE product_authentications (
    id UUID PRIMARY KEY,
    product_id UUID NOT NULL,
    requested_by BIGINT NOT NULL,
    appraiser_id BIGINT,
    status VARCHAR(20), -- PENDING, IN_REVIEW, APPROVED, REJECTED
    grade VARCHAR(5),   -- A+, A, B, C
    certificate_url TEXT,
    fee DECIMAL(10,2),
    created_at TIMESTAMP,
    completed_at TIMESTAMP
);
```

**API:**

```
POST /api/products/{productId}/authentication
GET  /api/products/{productId}/authentication
GET  /api/appraisers/{appraiserId}/pending-requests
POST /api/appraisers/{appraiserId}/complete-authentication
```

### 3.3 구매자 보호 프로그램

#### 3.3.1 에스크로 결제 강제

```

2. 판매자 발송
3. 구매자 수령 후 "검수 기간" (3일)
4. 이상 없으면 판매자에게 정산
5. 문제 있으면 반품/환불
```

#### 3.3.2 반품 보증 (선택 옵션)

판매자가 "7일 반품 보증" 옵션을 선택하면:
- 상품에 "반품 가능" 배지 표시
- 구매자 신뢰도 상승
- 플랫폼 수수료 1% 할인

### 3.6 입찰 예치금 사전 검증 강화

```
2. 자격 있는 사용자만 입찰 가능

3. 낙찰 시 즉시 결제 (예치금 차감)
```

**효과:**
- 장난 입찰 방지
- 낙찰 후 결제 포기율 감소

## 4. 효율성 개선 방안

### 4.1 Database 쿼리 최적화

#### 4.1.1 N+1 문제 해결

현재 경매 목록 조회 시 각 경매마다 Product 조회 발생 가능성:

```java
// AS-IS (N+1 발생)
List<Auction> auctions = auctionRepository.findAll();
for (Auction auction : auctions) {
    Product product = productClient.getProduct(auction.getProductId()); // N번 호출!
}

// TO-BE (Batch 조회)
List<Auction> auctions = auctionRepository.findAll();
List<UUID> productIds = auctions.stream()
    .map(Auction::getProductId)
    .toList();

Map<UUID, Product> products = productClient.getProductsByIds(productIds); // 1번 호출
```

#### 4.1.2 Redis 캐싱 전략

**캐시 대상:**

| 데이터 | TTL | 갱신 전략 |
|-------|-----|----------|
| 상품 상세 | 1시간 | Write-Through |
| 경매 목록 (페이지별) | 1분 | Write-Behind |
| 사용자 프로필 | 10분 | Cache-Aside |
| 인기 검색어 | 1시간 | Write-Behind |

**현재 Redis 사용:**
- Auction Service: WebSocket Pub/Sub만 사용
- 캐싱은 거의 미적용 → **개선 여지 큼**

**구현 예시:**

```java
@Cacheable(value = "auction", key = "#auctionId", unless = "#result == null")
public AuctionDetailResponse getAuctionDetail(String auctionId) {
    // DB 조회
}

@CacheEvict(value = "auction", key = "#auctionId")
public void updateAuction(String auctionId, AuctionUpdateRequest request) {
    // 업데이트 후 캐시 무효화
}
```

### 4.2 Kafka 메시지 처리 최적화

#### 4.2.1 배치 처리

현재는 메시지 1개씩 처리 → **대량 입찰 시 병목**

```java
// AS-IS
@KafkaListener(topics = "auction.bid.placed")
public void handleBid(BidPlacedEvent event) {
    // 1개씩 처리
}

// TO-BE (Batch)
@KafkaListener(topics = "auction.bid.placed",
               containerFactory = "batchKafkaListenerContainerFactory")
public void handleBids(List<BidPlacedEvent> events) {
    // 100개씩 일괄 처리
    batchUpdateAuctions(events);
}
```

#### 4.2.2 Dead Letter Queue (DLQ)

메시지 처리 실패 시 재시도 + DLQ:

```yaml
spring:
  kafka:
    listener:
      ack-mode: manual
    consumer:
      enable-auto-commit: false

# Retry 3회 실패 시 DLQ로 이동
spring.kafka.listener.default-error-handler:
  fixed-delay: 1000
  max-attempts: 3
  dlt-enabled: true
```

### 4.3 API Gateway 성능 개선

#### 4.3.1 응답 캐싱

자주 조회되는 API는 Gateway에서 캐싱:

```yaml
# 경매 목록 (status=LIVE)
spring.cloud.gateway.routes[0].filters:
  - LocalResponseCache=5m  # 5분 캐시
```

#### 4.3.2 WebFlux Non-Blocking

현재 동기 호출 → **WebFlux로 전환 고려**

```java
// AS-IS (Blocking)
Product product = productClient.getProduct(productId);
Auction auction = auctionClient.getAuction(auctionId);
return merge(product, auction);

// TO-BE (Non-Blocking)
Mono<Product> productMono = productClient.getProductAsync(productId);
Mono<Auction> auctionMono = auctionClient.getAuctionAsync(auctionId);

return Mono.zip(productMono, auctionMono)
    .map(tuple -> merge(tuple.getT1(), tuple.getT2()));
```

### 4.4 이미지 최적화

#### 4.4.1 이미지 리사이징

현재 원본 이미지 그대로 저장 → **용량 큼**

**개선:**
```
업로드 시:
1. 원본 저장 (S3)
2. 썸네일 생성 (300x300)
3. 상세 이미지 (1200x1200)
4. WebP 변환 (용량 30% 절감)
```

#### 4.4.2 CDN 적용

이미지는 CloudFront 등 CDN을 통해 제공:

```
AS-IS: Client → S3 (느림)
TO-BE: Client → CloudFront (Edge 캐싱, 빠름)
```

### 4.5 Database Connection Pool 튜닝

현재 기본 설정 사용 → **최적화 필요**

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20      # 기본 10 → 20
      minimum-idle: 10           # 유휴 연결 유지
      connection-timeout: 20000
      idle-timeout: 300000
      max-lifetime: 1200000

      # 연결 테스트
      connection-test-query: SELECT 1
```

**모니터링 메트릭:**
- `hikaricp.connections.active`
- `hikaricp.connections.idle`
- `hikaricp.connections.pending`
