# Biddy 시스템 아키텍처

## 개요
Biddy는 마이크로서비스 아키텍처 기반의 온라인 경매 플랫폼입니다.

## 주요 컴포넌트

### 1. Frontend
- **기술**: React, Vite, TailwindCSS
- **배포**: Vercel
- **기능**: 사용자 인터페이스, WebSocket 실시간 업데이트

### 2. API Gateway
- **기술**: Spring Cloud Gateway
- **기능**:
  - JWT 인증 필터
  - 라우팅
  - Rate Limiting
  - CORS 처리

### 3. Microservices
각 서비스는 독립적인 PostgreSQL 데이터베이스를 사용합니다.

#### Member Service
- 회원 가입/로그인
- JWT 토큰 발급
- 프로필 관리

#### Product Service
- 상품 등록/수정/삭제
- 상품 목록 조회
- 벡터 임베딩 (AI 검색용)

#### Auction Service
- 경매 생성/관리
- 실시간 입찰 처리
- WebSocket 실시간 알림
- **Outbox Pattern** 적용

#### Search Service
- Elasticsearch 기반 검색
- AI 기반 상품 추천
- 키워드 자동완성

#### Chat Service
- 판매자-구매자 실시간 채팅
- WebSocket (STOMP 프로토콜)
- 읽음 처리

#### Order Service
- 일반 주문 / 경매 낙찰 주문
- 주문 상태 관리
- 구매 확정
- 자동 취소 (경매 주문 24시간)

#### Payment Service
- Toss Payments API 연동
- 결제 생성/승인/취소/환불
- 판매자 정산 관리
- Webhook 처리

### 4. Data Layer

#### PostgreSQL
```mermaid
graph LR
    PG[PostgreSQL Container] --> DB1[biddy_member]
    PG --> DB2[biddy_product]
    PG --> DB3[biddy_auction]
    PG --> DB4[biddy_order]
    PG --> DB5[biddy_payment]
    PG --> DB6[biddy_chat]
    PG --> DB7[biddy_search]
```

#### Redis
- JWT 블랙리스트
- 세션 캐싱
- Rate Limiting 카운터

#### Elasticsearch
- 상품 검색 인덱스
- 키워드 자동완성
- 검색 히스토리

### 5. Message Queue (Kafka)

#### 주요 토픽
| Topic | Producer | Consumer | 설명 |
|-------|----------|----------|------|
| `auction.ended` | Auction Service | Order Service | 경매 종료 → 주문 생성 |
| `order.created` | Order Service | Payment Service | 주문 생성 → 결제 대기 |
| `payment.completed` | Payment Service | Order Service | 결제 완료 → 주문 상태 변경 |
| `payment.failed` | Payment Service | Order Service | 결제 실패 → 주문 취소 |
| `purchase.confirmed` | Order Service | Payment Service | 구매 확정 → 정산 처리 |

#### 패턴
- **Transactional Outbox Pattern**: 안정적인 이벤트 발행
- **Event-Driven Architecture**: 서비스 간 느슨한 결합

## 데이터 흐름

### 1. 경매 입찰 프로세스

```mermaid
sequenceDiagram
    actor User as 사용자
    participant FE as Frontend
    participant GW as API Gateway
    participant AS as Auction Service
    participant DB as PostgreSQL
    participant WS as WebSocket
    participant Redis as Redis

    User->>FE: 입찰 버튼 클릭
    FE->>GW: POST /api/v1/auctions/{id}/bids<br/>Authorization: Bearer {token}

    GW->>Redis: JWT 블랙리스트 확인
    Redis-->>GW: Not Blacklisted

    GW->>GW: JWT 검증 & X-Member-Id 추출
    GW->>AS: 요청 전달<br/>Header: X-Member-Id

    AS->>DB: BEGIN TRANSACTION
    AS->>DB: SELECT auction FOR UPDATE
    AS->>AS: 입찰가 검증
    AS->>DB: INSERT INTO bids
    AS->>DB: UPDATE auction SET current_bid
    AS->>DB: COMMIT

    AS->>WS: 브로드캐스트<br/>{type: "BID", currentBid, bidCount}
    WS-->>FE: WebSocket 메시지
    FE-->>User: 실시간 가격 업데이트

    AS-->>GW: 200 OK
    GW-->>FE: 200 OK
    FE-->>User: 입찰 성공 알림
```

### 2. 경매 종료 이벤트 처리 (Outbox Pattern)

```mermaid
sequenceDiagram
    participant Scheduler as Auction Scheduler
    participant AS as Auction Service
    participant DB as PostgreSQL
    participant Outbox as Outbox Relay<br/>Scheduler
    participant Kafka as Kafka
    participant PayS as Payment Service

    Note over Scheduler,AS: 경매 종료 시간 도달

    Scheduler->>AS: 경매 종료 처리
    AS->>DB: BEGIN TRANSACTION
    AS->>DB: UPDATE auction<br/>SET status='ENDED'
    AS->>DB: INSERT INTO outbox<br/>(event_type='AUCTION_ENDED')
    AS->>DB: COMMIT

    Note over Outbox: 5초마다 실행

    loop 미처리 이벤트 처리
        Outbox->>DB: SELECT * FROM outbox<br/>WHERE processed=false
        DB-->>Outbox: 이벤트 목록

        Outbox->>Kafka: publish(auction.ended, payload)
        Kafka-->>Outbox: ACK

        Outbox->>DB: UPDATE outbox<br/>SET processed=true
    end

    Kafka->>PayS: consume(auction.ended)
    PayS->>PayS: 낙찰자 주문 생성

    Note over PayS: Order Service 연동
    PayS->>Kafka: publish(order.created)
```

## 보안 아키텍처

### JWT 인증 흐름

```mermaid
flowchart TD
    Start([클라이언트 요청]) --> HasToken{Authorization<br/>헤더 있음?}

    HasToken -->|No| CheckWhitelist{WHITELIST<br/>경로?}
    HasToken -->|Yes| ValidateToken[JWT 토큰 검증]

    CheckWhitelist -->|Yes| Pass1[통과]
    CheckWhitelist -->|No| CheckOptional{Optional Auth<br/>경로 & GET?}

    CheckOptional -->|Yes| Pass2[통과<br/>X-Member-Id 없음]
    CheckOptional -->|No| Return401_1[401 Unauthorized]

    ValidateToken --> TokenValid{토큰 유효?}
    TokenValid -->|No| CheckOptional2{Optional Auth<br/>경로?}
    TokenValid -->|Yes| CheckBlacklist[Redis<br/>블랙리스트 확인]

    CheckOptional2 -->|Yes| Pass3[통과]
    CheckOptional2 -->|No| Return401_2[401 Unauthorized]

    CheckBlacklist --> IsBlacklisted{블랙리스트<br/>등록됨?}
    IsBlacklisted -->|Yes| CheckOptional3{Optional Auth<br/>경로?}
    IsBlacklisted -->|No| ExtractMemberId[memberId & role 추출]

    CheckOptional3 -->|Yes| Pass4[통과]
    CheckOptional3 -->|No| Return401_3[401 Unauthorized]

    ExtractMemberId --> AddHeaders[X-Member-Id<br/>X-Member-Role 헤더 추가]
    AddHeaders --> PassAuth[인증 통과]

    Pass1 --> End([서비스 호출])
    Pass2 --> End
    Pass3 --> End
    Pass4 --> End
    PassAuth --> End

    Return401_1 --> EndError([에러 반환])
    Return401_2 --> EndError
    Return401_3 --> EndError

    style Start fill:#e1f5e1
    style Pass1 fill:#e1f5e1
    style Pass2 fill:#e1f5e1
    style Pass3 fill:#e1f5e1
    style Pass4 fill:#e1f5e1
    style PassAuth fill:#e1f5e1
    style End fill:#e1f5e1
    style Return401_1 fill:#ffe1e1
    style Return401_2 fill:#ffe1e1
    style Return401_3 fill:#ffe1e1
    style EndError fill:#ffe1e1
```

### WHITELIST vs OPTIONAL_AUTH_GET_WHITELIST

| 경로 | 타입 | 인증 | X-Member-Id | 설명 |
|------|------|------|-------------|------|
| `/api/members/signup` | WHITELIST | 불필요 | 추가 안 함 | 회원가입 |
| `/api/members/login` | WHITELIST | 불필요 | 추가 안 함 | 로그인 |
| `/api/v1/auctions` | WHITELIST | 불필요 | 추가 안 함 | 경매 목록/상세 |
| `/api/members/{id}/nickname` | WHITELIST | 불필요 | 추가 안 함 | 닉네임 조회 |
| `/api/products` | OPTIONAL_AUTH | 선택적 | 토큰 있으면 추가 | 상품 목록 (찜 여부) |

## 성능 최적화

### 캐싱 전략

```mermaid
flowchart TD
    Request[API 요청] --> CheckCache{Redis<br/>캐시 확인}

    CheckCache -->|Hit| ReturnCache[캐시 데이터 반환]
    CheckCache -->|Miss| QueryDB[PostgreSQL 조회]

    QueryDB --> SaveCache[Redis에 캐싱<br/>TTL: 300s]
    SaveCache --> ReturnDB[데이터 반환]

    ReturnCache --> End([응답])
    ReturnDB --> End

    style CheckCache fill:#fff3e0
    style ReturnCache fill:#e8f5e9
```

### 데이터베이스 인덱스 전략

```sql
-- 경매 조회 최적화

CREATE INDEX idx_bid_auction_id ON bid(auction_id);
CREATE INDEX idx_bid_created_at ON bid(created_at DESC);

CREATE INDEX idx_outbox_processed ON outbox(processed, created_at);
```
