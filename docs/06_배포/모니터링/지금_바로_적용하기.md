```

```

배포 전 `kubectl describe node`의 Allocatable과 현재 requests를 확인하세요.

## 🚀 지금 바로 실행

### ⚠️ 중요: Swap을 메모리 증설처럼 간주하지 않기

Kubernetes의 기본 `NoSwap` 동작에서는 호스트에 Swap 파일만 추가해도 Pod가 그 Swap을
사용하지 못합니다. Swap은 K3s/kubelet의 `failSwapOn` 및 `memorySwap.swapBehavior`를
확인한 뒤 별도 운영 정책으로 적용해야 합니다. 우선 Pod requests를 수용할 실제 RAM이
있는지 확인하는 것이 안전합니다.

```bash
kubectl get nodes
kubectl describe nodes | sed -n '/Allocated resources:/,/Events:/p'
kubectl top nodes
```

## 🚑 기존 Targets 장애 복구

### 1. NetworkPolicy 적용

`biddy` namespace의 제한된 서비스가 `biddy-monitoring` namespace에서 들어오는
스크레이프 요청을 허용하도록 6개 정책을 적용합니다.

```bash
kubectl apply -f k8s/base/apigateway/networkpolicy.yaml
kubectl apply -f k8s/base/member/networkpolicy.yaml
kubectl apply -f k8s/base/product/networkpolicy.yaml
kubectl apply -f k8s/base/order/networkpolicy.yaml
kubectl apply -f k8s/base/auction/networkpolicy.yaml
kubectl apply -f k8s/base/payment/networkpolicy.yaml

kubectl get networkpolicy -n biddy
kubectl get namespace biddy-monitoring --show-labels
```

`biddy-monitoring` namespace에 `kubernetes.io/metadata.name=biddy-monitoring` 라벨이
있는지 확인합니다.

### 2. Kubelet `403 Forbidden` 해결

Kubelet의 `/metrics`는 `nodes/metrics` RBAC 권한이 필요합니다. 수정된 Prometheus
매니페스트를 다시 적용하고 ServiceAccount 권한을 확인합니다.

```bash
kubectl apply -f k8s/monitoring/prometheus.yaml

kubectl auth can-i get nodes/metrics \
  --as=system:serviceaccount:biddy-monitoring:prometheus
```

결과가 `yes`여야 합니다. RBAC 변경은 즉시 반영되므로 보통 Prometheus를 재시작할
필요가 없습니다. 30초 뒤 `kubernetes-nodes` Targets를 다시 확인합니다.

### 3. `connection refused`가 계속될 때

정책 적용 후에도 `connection refused`가 남으면 NetworkPolicy로 단정하지 않습니다.
Pod가 Running이어도 애플리케이션이 아직 포트를 열지 않았거나 재시작 중일 수 있습니다.

```bash
kubectl get pods -n biddy -o wide
kubectl get pods -n biddy \
  -o custom-columns='NAME:.metadata.name,READY:.status.containerStatuses[0].ready,RESTARTS:.status.containerStatuses[0].restartCount,LAST_REASON:.status.containerStatuses[0].lastState.terminated.reason'
kubectl get events -n biddy --sort-by='.lastTimestamp'

kubectl logs -n biddy deploy/apigateway --tail=200
kubectl logs -n biddy deploy/member --tail=200
kubectl logs -n biddy deploy/product --tail=200
kubectl logs -n biddy deploy/order --tail=200
kubectl logs -n biddy deploy/auction --tail=200
```

`OOMKilled`, 설정 서버 연결 실패, DB/Kafka 연결 실패, 포트 충돌을 먼저 확인합니다.
재시작 이력이 있으면 해당 Pod에 `kubectl logs <pod> --previous`도 실행합니다.

### 4. 최종 판정

```bash
kubectl port-forward -n biddy-monitoring svc/prometheus 9090:9090
```

`http://localhost:9090/targets`에서 다음을 구분해 확인합니다.

- `kubernetes-apiservers`: 1/1 UP
- `kubernetes-nodes`: 2/2 UP
- `kubernetes-cadvisor`: 2/2 UP
- `node-exporter`: 노드 수와 동일하게 UP
- `kube-state-metrics`: 1/1 UP
- `kubernetes-pods`: 애플리케이션 Pod의 현재 Ready 상태와 일치

### 왼쪽 메뉴 → Dashboards → Import

**현재 구성에서 바로 사용할 대시보드 2개**:

#### 1. JVM Micrometer (ID: 4701)

2. Dashboard ID에 `4701` 입력
3. Load 클릭
4. Prometheus 선택
5. Import 클릭

✅ **확인할 수 있는 메트릭**:

- GC (Garbage Collection) 시간
- 스레드 수
- 클래스 로딩 수

#### 2. Spring Boot Statistics (ID: 11378)
- 같은 방법으로 `11378` Import

✅ **확인할 수 있는 메트릭**:
- HTTP 요청 수 (초당)
- 평균 응답 시간
- 상태 코드별 요청 수 (2xx, 4xx, 5xx)
- Tomcat 스레드

#### 3. Kubernetes Cluster (ID: 6417)

`kube-state-metrics`가 배포된 뒤 Deployment, Pod, Node 상태 패널을 사용할 수 있습니다.

#### 4. Node Exporter Full (ID: 1860)

`node-exporter`가 모든 Linux 노드에 배포된 뒤 CPU, RAM, SWAP, 디스크, 네트워크
패널을 사용할 수 있습니다. 기존 설치에 exporter만 추가할 때는 다음을 실행합니다.

```bash
kubectl apply -f k8s/monitoring/node-exporter.yaml
kubectl apply -f k8s/monitoring/kube-state-metrics.yaml
kubectl apply -f k8s/monitoring/prometheus.yaml
kubectl rollout restart deployment/prometheus -n biddy-monitoring
kubectl rollout status deployment/prometheus -n biddy-monitoring
```

Prometheus 재시작은 변경된 scrape job을 읽기 위해 필요하며 PVC 데이터는 유지됩니다.

대시보드를 열기 전에 Prometheus UI에서 다음 쿼리가 각각 결과를 반환하는지 확인합니다.

```promql
container_cpu_usage_seconds_total
container_memory_working_set_bytes
node_uname_info
kube_node_info
kube_deployment_status_replicas
```

첫 두 쿼리는 `kubernetes-cadvisor`, `node_uname_info`는 `node-exporter`, 나머지
`kube_*` 쿼리는 `kube-state-metrics`가 제공합니다. 여기서 결과가 있는데 Grafana만
`No data`라면 Dashboard import 시 Prometheus datasource 선택과 `Job` 변수를 확인합니다.

## 🔍 유용한 Prometheus 쿼리

Prometheus UI (`http://localhost:9090`) → Graph 탭

### 1. 서비스별 HTTP 요청 수
```promql
sum(rate(http_server_requests_seconds_count[5m])) by (application)
```

### 2. 평균 응답 시간 (ms)
```promql
rate(http_server_requests_seconds_sum[5m]) / rate(http_server_requests_seconds_count[5m]) * 1000
```

### 3. JVM Heap 메모리 사용률
```promql
(jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"}) * 100
```

### 4. CPU 사용률 (Node Exporter)
```promql
100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) by (instance) * 100)
```

### 5. 메모리 사용률 (Node Exporter)
```promql
(1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100
```

## ⚠️ 문제 발생 시

### Pod가 Pending 상태로 멈춤

**확인**:
```bash
kubectl describe pod -n biddy-monitoring <pod-name>
```

**메시지에 `Insufficient memory`가 표시되면** Scheduler가 비교하는 것은 limit이
아니라 request입니다. 먼저 불필요한 워크로드를 정리하거나 노드 메모리를 증설합니다.
request를 낮춰야 한다면 실제 사용량을 측정한 뒤 `prometheus.yaml`과 `grafana.yaml`의
`resources.requests.memory`를 수정하고 다시 적용하세요. 호스트 Swap 추가만으로는
스케줄링 가능한 메모리가 늘어나지 않습니다.

### Grafana "No Data" 표시

**확인 1: Prometheus 로그**
```bash
kubectl logs -n biddy-monitoring -l app=prometheus
```

**확인 2: Prometheus Targets**
```bash
kubectl port-forward -n biddy-monitoring svc/prometheus 9090:9090
```

브라우저: `http://localhost:9090/targets`

**확인 3: Actuator 엔드포인트**
```bash
kubectl exec -n biddy <pod-name> -- curl \
  localhost:<service-port>/actuator/prometheus
```

## 🎯 다음 단계

### 1. 알림(Alert) 확인 ⭐ 중요!

`alerting-rules.yaml`의 규칙은 Prometheus에 로드됩니다. Node Exporter가 배포되면
노드 메모리/디스크 규칙에 필요한 `node_*` 메트릭도 수집됩니다. 단, Alertmanager가
배포되어 있지 않아 Prometheus 규칙을 외부 채널로 전송하지 않습니다.

#### Prometheus에서 Alert 확인
```
http://<node-ip>:30090/alerts
```

우선 `PrometheusTargetDown`, `HighErrorRate`, `HighLatency`, `NodeMemoryPressure`,
`HighDiskUsage` 규칙의 쿼리 결과를 Prometheus UI에서 검증하세요.

### 2. Slack/Discord 알림 연동 (추가 구성 필요)

Grafana 자체 Alert rule을 만들 경우에는 Grafana Contact point를 사용할 수 있습니다.
현재 Prometheus의 `alerting-rules.yaml`을 그대로 외부 전송하려면 Alertmanager 배포와
Prometheus `alerting.alertmanagers` 설정이 별도로 필요합니다.

#### Grafana → Alerting → Contact points
1. **Add contact point** 클릭
2. **Name**: "Slack Alerts" (또는 "Discord Alerts")
3. **Integration**: Slack 또는 Discord 선택
4. **Webhook URL**: Slack/Discord에서 발급받은 Webhook URL 입력
5. **Test** 클릭하여 테스트 메시지 전송
6. **Save contact point**

#### Slack Webhook URL 발급 방법
```
1. https://api.slack.com/apps 접속
2. "Create New App" → "From scratch"
3. App 이름 입력 (예: "Biddy Monitoring")
4. Workspace 선택
5. "Incoming Webhooks" → Activate
6. "Add New Webhook to Workspace"
7. 알림 받을 채널 선택
8. Webhook URL 복사
```

#### Discord Webhook URL 발급 방법
```
1. Discord 서버 설정 → 연동
2. "웹후크" → "새 웹후크"
3. 웹후크 이름 입력 (예: "Biddy Monitoring")
4. 채널 선택
5. "웹후크 URL 복사"
```
