# 보안·신뢰성·성능 설계

## 1. 보안 경계

### 1.1 인증과 신뢰 전달

**[구현]** Gateway가 JWT를 검증하고 사용자 ID/역할 헤더를 추가한다. 일부 서비스는 공통 `HeaderAuthenticationFilter`, 일부는 자체 헤더/JWT 필터, Controller 직접 헤더 접근을 혼용한다.

**[목표]** 외부 요청에서 들어온 `X-Member-Id`, `X-Member-Role`을 Gateway가 항상 제거한 뒤 검증 결과로 새로 설정한다. 서비스 포트는 private network에서만 접근 가능하게 하고, 내부 호출은 mTLS 또는 workload identity로 발신 서비스를 식별한다. downstream은 “헤더가 존재함”이 아니라 “Gateway 또는 허용된 서비스가 보냄”을 신뢰 근거로 삼는다.

### 1.2 권한 모델

| 자원 | 읽기 | 쓰기/상태 변경 |
|---|---|---|
| 공개 상품·경매 | 익명 허용, 로그인 시 개인화 | 소유 판매자 또는 관리자 |
| 회원 프로필 | 본인, 필요한 최소 공개 정보 | 본인; 정지/탈퇴 승인은 관리자 |
| 주문 | 구매자, 제한적 판매자 관점 | 상태별 담당 주체만 |
| 결제·예치금 | 본인 | 결제 당사자, 관리자 조정은 ADMIN + 감사로그 |
| 정산 | 해당 판매자 | 월 정산 실행은 내부 scheduler/admin |
| 채팅 | 방의 buyer/seller | 방 참여자만 |
| Debug/Batch/Reingest | 운영 공개 금지 | 내부 운영자 전용 |

Object-level authorization을 모든 상세/수정 API에서 검증한다. ID를 바꿔 다른 사용자의 주문·결제·채팅을 조회하는 BOLA 테스트를 필수로 둔다.

### 1.3 비밀과 개인정보

- 운영 secret은 Git/이미지/YAML 기본값에 두지 않고 Secret Manager 또는 Kubernetes Secret + 암호화 저장소에서 주입한다.
- 현재 Chat JWT 고정 기본값, Gateway/Auction 개발 기본값, DB 기본 계정은 `local` profile로 제한한다.
- 로그에서 JWT, password, mail credential, Toss key/paymentKey, AI key, 이메일·전화번호 전체를 마스킹한다.
- 검색 이력과 AI 질의에는 개인정보가 포함될 수 있으므로 보존 기간, 삭제 API, 외부 AI 전송 고지를 정의한다.
- 관리자 예치금 조정, 환불, 정산 실행에는 actor/reason/before/after/correlationId를 가진 불변 감사 이벤트를 남긴다.

## 2. 신뢰성 패턴

### 2.1 Outbox와 소비 멱등성

**[구현]** Member, Auction, Order, Payment에는 Outbox가 있다. Product의 경매 등록과 재고 실패 이벤트는 `KafkaTemplate`로 직접 전송한다. Product는 `ProcessedOrder`로 재고 차감 중복을 일부 방지한다.

**[목표]** 모든 상태 변경 이벤트를 같은 로컬 트랜잭션의 Outbox에 기록한다. 공통 이벤트 envelope는 `eventId`, `eventType`, `eventVersion`, `aggregateType`, `aggregateId`, `occurredAt`, `producer`, `traceId`, `payload`를 포함한다. 소비자는 inbox/processed-event에 `eventId` unique constraint를 두고 비즈니스 반영과 함께 커밋한다.

Outbox relay는 다중 replica에서 `FOR UPDATE SKIP LOCKED` 또는 lease로 중복 pick을 제한하되, Kafka 중복 전달은 여전히 가능하다고 가정한다. FAILED 이벤트 재처리 도구, backlog/oldest-age 경보, 보존/정리 정책을 둔다.

### 2.2 재시도와 DLQ

- transient 오류만 exponential backoff + jitter로 제한 재시도한다.
- validation/schema/권한 오류는 재시도하지 않고 DLQ에 원문, 예외, consumer version을 함께 보낸다.
- consumer가 broad `catch` 후 로그만 남기고 offset을 커밋하지 않도록 한다.
- 순서가 필요한 aggregate 이벤트는 `aggregateId`를 Kafka key로 사용한다.
- DLQ replay는 동일 멱등 키를 유지하고 운영자 승인·감사 기록을 남긴다.

### 2.3 동기 호출

Search→Product, Payment→Order, Order→Product 호출에는 요청별 deadline을 전파한다. 기본 권고는 내부 connect 300ms, read 1~2s 범위에서 부하 시험으로 확정하고 최대 1회의 jittered retry만 허용한다. 결제처럼 비멱등 상태 변경은 호출 자체를 재시도하기 전에 idempotency contract가 있어야 한다.

Circuit breaker가 열리면 Search는 추천 없이 기본 검색 또는 명확한 503으로 degrade할 수 있지만, Payment는 성공으로 추정해서는 안 된다. Toss timeout은 상태 미확정으로 저장하고 paymentKey 조회/reconciliation으로 확정한다.

## 3. 동시성 설계

| 시나리오 | 현재 제어 | 추가 보강 |
|---|---|---|
| 같은 경매 동시 입찰 | Auction 비관적 락 | 락 대기 timeout, p99 측정, 마감시각 DB 기준 |
| 같은 상품 재고 차감 | Product `@Version` | 제한 재시도, 중복 key를 orderId+productId로 확장 |
| 같은 주문 중복 결제 | Redis order lock/idempotency | DB unique(orderId), lease 소유권 검증, reconciliation |
| 예치금 동시 변경 | account `@Version` + 원장 | 거래 idempotency key, DB retry, 잔액-원장 대사 |
| 중복 채팅방 생성 | 명시 제약 확인 필요 | unique(productId,buyerId,sellerId) |
| 다중 경매 종료 scheduler | 상태 조회/트랜잭션 | DB claim/skip locked, 단일 낙찰 이벤트 unique |

## 4. 성능 설계

### 4.1 초기 SLO 제안

| 기능 | 가용성 | 지연시간 목표 |
|---|---:|---:|
| 상품/경매 조회 | 월 99.9% | p95 300ms, p99 800ms |
| 입찰 접수 | 월 99.95% | p95 250ms, p99 700ms |
| 결제 요청 접수 | 월 99.95% | 내부 처리 제외 p95 500ms |
| 채팅 전달 | 월 99.9% | 서버 처리 p95 300ms |
| 검색 | 월 99.5% | AI 포함 p95 2.5s |
| Kafka 핵심 이벤트 | 성공 99.99% | 발행→소비 p95 5s |

수치는 목표 초안이며 k6/운영 트래픽 결과로 확정한다. 평균이 아니라 p95/p99와 오류율을 함께 본다.

### 4.2 병목별 전략

- 경매 피드는 `(status, ends_at)`, 입찰은 `(auction_id, created_at desc)`, 관심은 `(member_id, created_at desc)` 인덱스를 둔다.
- 주문·결제 조회는 소유자+생성시각, 상태+만료시각 복합 인덱스를 사용한다.
- Outbox는 `(status, created_at)` 인덱스와 batch limit가 필요하다.
- Chat 메시지는 `(room_id, id desc)` cursor pagination을 사용하고 offset deep paging을 피한다.
- AI embedding은 상품 내용 hash로 중복 생성을 피하고 queue 기반 비동기 갱신, rate limit, 비용 메트릭을 둔다.
- 피드/관심 cache는 source of truth가 아니며 cache miss와 Redis 장애 때 DB로 안전하게 복귀한다.

## 5. 관측과 장애 대응

모든 HTTP/Kafka/STOMP에 `traceId` 또는 `correlationId`를 전파한다. 핵심 메트릭은 API RED(rate/errors/duration), JVM/DB pool, Kafka consumer lag, Outbox pending/oldest age/failures, Redis hit/error, 입찰 충돌, 결제 불일치, AI latency/token/cost다.

P0 경보는 중복 결제 의심, 원장 불일치, 낙찰 주문 미생성, 인증 우회, Outbox FAILED다. P1은 consumer lag, 핵심 API error budget burn, DB pool 고갈, Redis/Kafka 장애다. 각 경보는 담당자·진단 쿼리·완화·복구·사후 검증을 가진 runbook으로 연결한다.
