# 플랫폼 서비스 상세설계

## 1. 구성요소

| 모듈 | 포트 | 현재 책임 |
|---|---:|---|
| `apigateway` | 8000 | WebFlux routing, CORS, JWT/blacklist, Swagger 집계 |
| `discovery` | 8761 | Eureka registry/dashboard |
| `config` | 8888 | native Config Server; 현재 공통 설정은 빈 객체 |
| `common` | 실행 없음 | header→Spring Authentication 변환 library |

## 2. API Gateway

Gateway는 인증, 외부 경로, CORS, response header 중복 제거의 정책 집행점이다. 인증 필터는 공개/선택/필수 인증을 구분하고 유효 토큰이면 downstream 사용자 헤더를 전달한다.

목표 filter chain은 request ID 부여 → 외부 `X-Member-*` 제거 → body size/rate limit → JWT/blacklist → authorization coarse policy → 라우팅 → 보안 응답 헤더/관측 순서다. Redis blacklist 장애를 fail-open으로 둘지 fail-closed로 둘지는 경로 위험도에 따라 구분한다. 결제·관리자는 fail-closed, 공개 조회는 JWT 서명만으로 제한적 degrade할 수 있다.

현재 라우팅 정합성 개선:

- Auction `/ws`에 대응하는 WebSocket route 추가 또는 서비스 endpoint 변경
- Swagger 집계에 Chat 포함
- 내부 Payment↔Order, vector search, batch/debug/admin API를 외부 route에서 분리
- 공개 경로를 문자열 prefix가 아니라 method+정확 pattern test로 검증
- CORS의 `*.vercel.app`은 preview 배포 전체 허용 위험을 평가하고 allow-list화

## 3. Discovery

개발에서는 단일 Eureka로 충분하지만 운영 단일 인스턴스는 새 instance 등록과 장애 복구의 단일 실패점이다. 운영 선택지는 Eureka peer 2~3개 또는 Kubernetes Service/DNS로 탐색을 단순화하는 것이다. Kubernetes를 주 배포 환경으로 확정하면 중복 service discovery 계층의 운영 비용을 비교해 ADR로 결정한다.

health는 process 생존(liveness)과 traffic 준비(readiness)를 분리한다. Eureka 미등록만으로 이미 받은 요청을 처리할 수 없는 것은 아니며, startup dependency를 과도하게 직렬화하지 않는다.

## 4. Config

현재 Config Server는 골격만 있고 대부분 설정은 각 서비스 YAML과 환경변수에 있다. 유지한다면 환경별 non-secret 설정의 단일 원본, validation, 버전 pin, startup fail policy와 refresh 영향 분석이 필요하다. secret은 Config Git 저장소가 아니라 secret manager가 소유한다.

실질적으로 사용하지 않는다면 장애면과 혼란을 줄이기 위해 제거하는 편이 낫다. “유지해 둘 수도 있음”이 아니라 중앙 설정 도입 또는 제거를 ADR로 확정한다.

## 5. Common library

공통 모듈은 기술 횡단 관심사만 포함한다. 현재 header 인증 filter 범위는 적절하지만 서비스별 복제 구현과 principal 사용법을 통일해야 한다. 도메인 Entity, repository, event payload를 넣지 않는다. 오류 envelope/trace propagation 같은 공통 코드는 작은 독립 library로 versioning하고 각 서비스가 선택적으로 upgrade한다.

## 6. 수용 기준

- 외부 클라이언트가 사용자 헤더를 위조해도 downstream principal이 바뀌지 않는다.
- Gateway route/OpenAPI/WebSocket smoke test가 모든 서비스에 대해 자동화된다.
- Discovery/Redis 장애 시 경로별 fail-open/closed 정책이 테스트된다.
- 운영 설정에는 개발 기본 secret과 `ddl-auto:update`가 없다.
- Config/Eureka의 운영 채택 여부와 HA/제거 계획이 ADR로 승인된다.
