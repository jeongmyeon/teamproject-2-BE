# 리스크와 개선 로드맵

## 1. 우선순위 기준

- **P0**: 금전/재고 오류, 인증 우회, 데이터 유실처럼 운영 전 차단해야 하는 위험
- **P1**: 장애 복구와 확장 시 높은 확률로 문제가 되는 위험
- **P2**: 유지보수성과 비용을 개선하는 항목

## 3. 단계별 실행 계획

### Phase 0 — 운영 차단 위험 제거 (1~2주)

- 모든 privileged/debug/batch/reingest endpoint inventory와 deny-by-default 권한 테스트
- Gateway 외 서비스 외부 접근 차단, 사용자 헤더 제거·재주입
- 운영 secret 기본값 제거와 secret scan
- Payment DB unique/order reconciliation 설계와 긴급 대사 쿼리
- Auction WebSocket route, Chat Swagger, route smoke 정합화
- 운영 `ddl-auto=validate`, migration 도구 도입 시작

**종료 조건:** 인증 위조·관리 API 침투 테스트 통과, 중복 결제 통합 테스트 통과, 모든 서비스 경로 smoke 통과.

### Phase 1 — 분산 일관성 표준화 (2~4주)

- versioned event envelope/JSON Schema와 topic catalog 확정
- Product 직접 발행을 Outbox로 변경
- 소비자 Inbox/eventId 멱등, retry/DLQ/replay 도입
- Outbox relay의 retry/FAILED/claim/purge/메트릭 표준화
- Order-Product-Payment-Auction Saga duplicate/order reversal chaos test

**종료 조건:** Kafka 중단·중복·순서 역전·pod kill 후 데이터가 자동 또는 runbook으로 수렴.

### Phase 2 — 관측성과 운영 자동화 (2~3주)

- OpenTelemetry trace와 correlation propagation
- 핵심 SLO/dashboard/error-budget alert, Outbox/lag/금전 불일치 metric
- immutable image digest 배포, migration job, canary와 synthetic test
- backup restore drill과 Payment/Order/ledger reconciliation scheduler

**종료 조건:** P0/P1 경보가 runbook과 연결되고 staging game day에서 탐지·복구 시간을 측정.

### Phase 3 — 성능·AI·실시간 고도화 (지속)

- 입찰/결제/채팅/Outbox 부하 시험 기반 index·pool·partition 조정
- Chat durable delivery 필요성 결정과 읽음 cursor 개선
- Search/Chatbot evaluation gate, cache, quota, corpus blue-green
- Config/Eureka 존치 ADR, Kubernetes native 대안 평가
- API v1/error envelope/내부 API namespace 정리

## 5. 추적 가능한 작업 단위 예시

각 개선 이슈는 “문제/근거 → 영향 → 선택지 → 결정 → 코드·migration·계약 → 테스트 → metric/alert → rollout/rollback”을 포함한다. 단순히 “Outbox 적용”으로 끝내지 말고 `order.stock.deduct.failed`가 DB 변경과 원자적으로 저장되고, 동일 event replay가 한 번의 효과를 내며, backlog alert와 재처리 절차가 검증되는 것까지 완료 조건으로 둔다.

## 6. 최종 목표 상태

Biddy의 목표는 모든 서비스를 동일한 패턴으로 재작성하는 것이 아니다. 금전·재고·낙찰에는 강한 무결성과 대사 가능성을, 검색·추천·실시간 UI에는 명시적 최종 일관성과 degrade 가능성을 적용한다. 각 서비스는 독립적으로 배포할 수 있고 계약은 버전으로 진화하며, 장애가 발생해도 데이터가 유실되지 않고 운영자가 관측·재처리·검증할 수 있어야 한다.
