# 설계 원칙과 판정 기준

## 1. 목적과 범위

이 문서는 Biddy의 설계를 읽고 변경할 때 적용할 공통 판단 규칙을 정의한다. 범위는 저장소에 포함된 Java 서비스, 인프라 설정, API·이벤트·데이터 계약이다. `frontend/`에는 `.gitkeep`만 있으므로 UI 내부 구현은 검증 범위에서 제외하고 백엔드 연동 계약만 설계한다.

## 2. 근거 우선순위

서로 다른 설명이 충돌하면 다음 순서로 판정한다.

1. 실행 코드와 테스트
2. 서비스 `application*.yml`, Gradle, Docker/Kubernetes, CI 설정
3. 이번 `docs_gpt56`
4. 기존 `docs_codex`
5. 기존 `docs`

문서가 구현과 다르면 구현을 AS-IS로 기록하고, 바람직한 동작은 TO-BE로 분리한다. 예를 들어 Auction의 `auction.ended`는 현재 Outbox에 저장되므로 과거의 “직접 Kafka 발행” 설명보다 현 코드를 따른다.

## 3. GPT-5.6 관점의 10가지 원칙

1. **사실과 제안을 분리한다.** 존재하지 않는 기능을 현재 기능처럼 적지 않는다.
2. **도메인 소유권을 단일화한다.** 다른 서비스의 테이블을 직접 읽지 않고 API 또는 이벤트 계약을 사용한다.
3. **상태 전이를 명시한다.** 주문·결제·경매·정산은 허용 전이와 거부 전이를 코드와 테스트에 함께 둔다.
4. **분산 처리는 at-least-once를 전제로 한다.** 생산자는 Outbox, 소비자는 `eventId` 기반 멱등 처리로 중복과 유실을 함께 다룬다.
5. **동기 호출에는 시간 예산이 있다.** connect/read timeout, 제한된 재시도, circuit breaker, fallback 여부를 계약에 포함한다.
6. **인증과 권한을 분리한다.** JWT가 유효하다는 사실과 해당 자원에 접근할 권한이 있다는 사실은 별도로 검증한다.
7. **관측 가능하지 않은 기능은 운영 준비가 아니다.** trace/correlation ID, 구조화 로그, 핵심 메트릭, 경보, runbook을 완료 조건에 넣는다.
8. **스키마 변경은 이력으로 관리한다.** 운영에서는 `ddl-auto:update`가 아니라 Flyway/Liquibase의 순방향 migration을 사용한다.
9. **AI 기능은 비결정적 외부 의존성이다.** 타임아웃·비용·개인정보·품질평가·비활성화 경로를 설계한다.
10. **완료는 검증 가능해야 한다.** 정상 시나리오뿐 아니라 동시성, 중복, 순서 역전, 외부 장애, 재시작 후 복구를 테스트한다.

## 4. 품질 속성 우선순위

| 우선순위 | 속성 | Biddy에서의 의미 | 대표 지표 |
|---:|---|---|---|
| P0 | 금전·재고 정확성 | 중복 결제/이중 차감/잘못된 낙찰 방지 | 불일치 0건, ledger reconciliation |
| P0 | 보안 | 사용자 헤더 위조, 관리자 API 노출, 비밀 유출 방지 | 인증 우회 0건, secret scan 통과 |
| P1 | 이벤트 전달 신뢰성 | 주문·결제·정산 흐름의 유실 방지 | Outbox backlog, DLQ count |
| P1 | 가용성 | 핵심 조회·입찰·결제의 지속 제공 | 서비스별 availability SLO |
| P1 | 지연시간 | 마감 근처 입찰과 알림 지연 최소화 | API p95/p99, event lag |
| P2 | 변경 용이성 | 서비스별 독립 배포와 계약 호환 | contract test, change failure rate |
| P2 | 비용 | AI 호출·검색·로그·인프라 비용 통제 | 호출당 비용, cache hit ratio |

## 5. 문서별 필수 항목

도메인 상세설계서는 최소한 다음을 포함한다.

- 책임과 비책임, 소유 데이터
- 외부 API와 내부 통합점
- 핵심 상태와 불변식
- 대표 시퀀스
- 동시성·멱등성·장애 처리
- 보안 경계
- 구현과 목표의 차이
- 수용 기준과 필수 테스트

## 6. 변경 의사결정 기준

새 동기 서비스 호출은 사용자 요청에 즉시 필요한 데이터일 때만 추가한다. 최종 일관성이 허용되고 독립적인 후속 처리가 가능하면 이벤트를 우선한다. 이벤트를 추가할 때는 생산자·소유자·소비자·키·스키마 버전·재처리 정책을 동시에 정의한다.

공통 라이브러리에는 인증 헤더 변환 같은 기술 횡단 관심사만 둔다. 도메인 Entity나 이벤트 DTO를 공통 모듈에 넣어 서비스 배포를 컴파일 타임으로 결합하지 않는다. 계약 공유가 필요하면 버전이 있는 OpenAPI/AsyncAPI/JSON Schema artifact를 사용한다.

## 7. Definition of Done

설계 변경은 다음 조건을 모두 만족할 때 완료로 본다.

- 요구사항과 변경된 경계·상태·계약이 문서화되어 있다.
- 단위, 통합, 계약 테스트가 자동화되어 있다.
- migration과 rollback/roll-forward 절차가 있다.
- 로그에 비밀/개인정보가 남지 않고 권한 테스트를 통과한다.
- 대시보드, 경보 임계값, 장애 대응자가 정의되어 있다.
- 배포 후 확인할 synthetic 또는 smoke 검증이 있다.
