# 테스트 전략

## 1. 현재 진단

현재 `src/test` 파일 수는 대략 Auction 11, Payment 9, Order 2이고 Member/Product/Search 및 플랫폼 모듈은 각 1개 수준이며 Chat/Chatbot에는 테스트 파일이 없다. 파일 수가 품질을 직접 뜻하지는 않지만 금전·재고·인증·AI·실시간 경로 대비 자동 검증의 분포가 불균형하다.

## 2. 테스트 피라미드

| 계층 | 목적 | 도구/범위 |
|---|---|---|
| Domain unit | 상태 전이·불변식·금액 계산 | JUnit 5, parameterized/property test |
| Application unit | use case orchestration와 실패 분기 | Mockito는 외부 port에만 |
| Persistence integration | 제약·lock·query·migration | Testcontainers PostgreSQL/pgvector |
| Messaging integration | Outbox/Inbox, duplicate, retry, DLQ | Testcontainers Kafka |
| API/contract | HTTP 상태·schema·권한·호환 | MockMvc/WebTestClient, OpenAPI diff, Pact |
| Realtime | CONNECT/SUBSCRIBE/SEND, Redis fan-out | 실제 STOMP client + Redis container |
| E2E | 핵심 사용자 여정 | Compose/K8s ephemeral environment |
| Performance/chaos | SLO와 복구 | k6, Toxiproxy/장애 주입 |

## 3. 위험 기반 필수 시나리오

### P0: 금전·재고·낙찰

- 100개 동시 입찰에서 하나의 직렬화된 최종가와 낙찰자가 나온다.
- 동일 payment idempotency key 100회 요청이 한 승인·한 원장 효과를 낸다.
- provider timeout/성공 응답 유실 후 reconciliation이 정확한 상태로 수렴한다.
- 동일 Kafka 이벤트 반복·순서 역전·재시작에도 주문/재고/정산이 중복되지 않는다.
- 부분 취소 합계, 잔액, 거래 원장, 정산 합계의 property가 항상 성립한다.

### P0: 보안

- 외부 `X-Member-Id/Role` 위조, 만료/변조 JWT, blacklist, refresh replay.
- 모든 자원 ID에 대한 BOLA와 관리자 API role escalation.
- WebSocket 비참여 room/auction destination 구독·전송.
- debug, batch, adjust, settlement, reingest 운영 외부 접근 차단.
- secret scan, dependency/SBOM, container image scan.

### P1: 가용성·복구

- Kafka down 동안 Outbox backlog 후 재기동 발행.
- Redis down에서 경로별 fail-open/closed 및 DB fallback.
- Product/Order/Toss/OpenAI/Gemini timeout, circuit breaker, fallback.
- 다중 scheduler replica, pod 강제 종료, DB connection pool 고갈.
- WebSocket disconnect/reconnect와 gap recovery.

## 4. AI 품질 검증

검색은 고정 catalog와 질의 세트로 Recall@K/NDCG, 후보 외 hallucination, latency/cost를 측정한다. 챗봇은 versioned FAQ corpus로 correctness, groundedness, citation, refusal, prompt injection을 평가한다. 외부 모델 실호출 smoke는 nightly/manual로 제한하고 PR에서는 recorded contract 또는 deterministic fake를 사용한다.

모델·prompt·chunking 변경은 평가 결과를 artifact로 남기고 기준 미달이면 merge를 차단한다.

## 5. 성능 시험

기존 `k6-tests`의 smoke/business/concurrency 경매 시나리오를 CI nightly와 배포 전 환경으로 확장한다.

| 시나리오 | 측정 |
|---|---|
| 경매 마감 집중 | 입찰 p95/p99, lock wait, reject 정확성, WS lag |
| 결제 burst | duplicate effect, Redis/DB contention, provider call 수 |
| 검색 | AI on/off latency, fallback rate, 비용, Product pool |
| 채팅 fan-out | 동시 연결, delivery lag, Redis throughput, reconnect |
| Outbox backlog | drain rate, oldest age, DB/Kafka 부하 |
| Batch | chunk 처리량, online API 영향, restartability |

## 6. CI 품질 게이트

PR마다 변경 모듈 compile/unit/integration, migration, OpenAPI/이벤트 schema 호환, formatter/static analysis, secret/dependency scan을 수행한다. merge 전 핵심 contract test를 전체 서비스 조합으로 실행한다. image에는 immutable SHA tag를 사용하고 SBOM/서명을 생성한다.

현재 workflow는 서비스별 build/image push를 수행하지만 path filter로 인해 공통 Gradle/계약 변경의 영향을 놓칠 수 있다. root settings, wrapper, common, schema 변경 시 영향 서비스 전체 CI가 실행되도록 dependency map을 추가한다.

## 7. 릴리스 수용 기준

- P0 suite 100% 통과, flaky test 0개.
- migration을 production-like snapshot에서 실행·검증.
- 핵심 SLO threshold와 이전 release 대비 성능 회귀 허용치 통과.
- 새 이벤트 consumer가 replay와 duplicate fixture를 통과.
- rollback보다 roll-forward가 안전한 데이터 변경은 복구 절차를 rehearsal.
- smoke: 가입→상품→주문/경매→결제→구매확정/정산과 채팅·검색 핵심 경로.
